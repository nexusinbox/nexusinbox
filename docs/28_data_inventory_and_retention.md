# 28. 運営が持つデータの棚卸しと保持期限

**Status**: Accepted、実施済み (2026-11-07〜08。保持期限は 90 日で enforce。§5 の P1〜P3 はすべて対応した)
**Scope**: 運営側 (API / DB / R2 / ログ / 委託先) が持つデータの全量と、保持する理由・期限・減らし方
**Related**: [02 データモデル](./02_data_model.md)、[06 BYOS](./06_storage_byos.md)、[17 添付](./17_attachment_upload_r2_spec.md)、[18a Runbook §11](./18_production_bootstrap_runbook.md)、[23 鍵管理](./23_key_management_policy.md)、[29 Isolated mode 自動返信の復旧](./29_isolated_auto_reply_recovery.md)

## 1. 前提となる決定 (2026-11-07)

1. **運営は鍵を預からない。** 秘密鍵はブラウザ (IndexedDB) か、利用者のマシンの Signer Daemon にだけ置く。今もサーバは秘密鍵を持っていない。`agent_credentials.key_holder` は置き場所を記録しているだけ。機密計算 (TEE) で運営が鍵を預かる案は採らない。理由は次のとおり。
   - 見えない形にしても、全員分の鍵を一か所で預かることになる。破られたときの被害が全員に及ぶ
   - TEE も物理攻撃で破られた例がある。2025-10 の TEE.fail では、Intel と AMD の機密計算から証明用の鍵が取り出された。両社とも物理攻撃は対象外という立場
   - 「運営にも読めない」と保証するには、更新のたびに、動いているコードを外部から検証できる体制が要る。個人運営では維持できない
2. **運営が持つデータを最小限にし、すべてに期限を付ける。** 持つのは、配送・乱用防止・本人確認・画面表示に要るものだけ。期限が来たら消すのは運営の手作業ではなく、コードと設定で担保する。
3. **持たないこと自体を防御にする。** 本文は受信側の固定の鍵で包んでいる ([keywrap.ts](../apps/web/lib/crypto/keywrap.ts))。その鍵が後で漏れると、サーバに残っている過去の暗号文はすべて読める。残していなければ読まれない。
4. **サーバは配送路であって、保管庫ではない。** 合意の記録など長く残したいものは、利用者側に保存する。
5. **本人確認は一意の人間を土台にする。** 今のログインは World ID の Orb だけを受け付けている (`services/api/src/lib.rs` の `is_valid_verification_level`)。将来ほかの証明手段に差し替える場合も、運営が受け取るのはサービス内で一意な識別子だけにする。氏名や住所などの個人情報は受け取らない。差し替えの仕組みは別の ADR で設計する。

## 2. 着手前の状況 (2026-11-07 朝に確認)

以下は着手前の記録。すべて §5 で対応した。

- **本番の設定**: `/status` は `storage_backend: "s3"` (Cloudflare R2)、`auto_purge_enabled: false` を返す
- **削除する経路の無いテーブル**: `users`、`sessions`、`agent_tokens`、`agent_audit_log`、`attachment_uploads` の 5 つ。lib.rs に `DELETE FROM` が無く、増え続ける
- **自動パージは事実上動かない**:
  - `POST /admin/purge/run` からしか起動できず、定期実行の仕組みが無い
  - 条件のうち、`ai_category` が `background` / `low_priority` になる経路が無い。有効にしても効くのは「アーカイブ済みで 90 日経過」だけ
  - その場合も行は消えず、墓標として残る
- **R2 に孤立した本文が残る**: メッセージ削除は索引行を先に消し、それから R2 を消す。R2 の削除に失敗すると本文だけが残り、それを拾う仕組みは無い
- **監査ログに IP が残る**: `detail` に IP とユーザーエージェントが入る。ユーザーエージェントは長さの上限が無い。対象はトークン・クレデンシャル系と添付系のイベント。専用の `ip_address` 列は使われていない
- **プライバシーポリシーと実態がずれている** (§6)

## 3. 棚卸し

形式欄の区分は、平文 / ハッシュ / 暗号文 (運営は読めない) / 公開鍵。

### 3.1 本文と添付 (R2)

| データ | 中身 | 形式 | 必要な理由 | 今の保持 | 目標 |
|---|---|---|---|---|---|
| メッセージ本文 `<prefix>/<message_id>.json` | `encrypted_content`、`encrypted_key`、`nonce`、`content_type` | 暗号文。`content_type` だけ平文 | 受信者への配送と再表示 | 利用者が消すまで無期限。送信者と受信者の 2 行で 1 つを共有する | 作成から 90 日で削除 |
| 添付 `attachments/<id>/blob.bin` | 暗号化済みのファイル (最大 5 MiB) | 暗号文。キーと S3 メタデータに user_id も下書き ID も入らない (2026-11-07 から。それ以前のオブジェクトは 97 日のルールで消える) | 同上 | メッセージが消えるまで。添付されなかったものは 24 時間で掃除 | 本文と同時に削除 |

### 3.2 関係性のメタデータ (Postgres)

| テーブル | 主な中身 | 必要な理由 | 今の保持 | 目標 |
|---|---|---|---|---|
| `message_index` | 送受信者の DID、時刻、スレッド、状態、フォルダ、スター、優先度、信頼スコア、自動返信の判定。件名は暗号文 | 受信箱の一覧、スレッド、自動返信 | 無期限。自動パージも墓標として行を残す | 本文と同時に行ごと削除し、墓標は残さない |
| `message_attachments` | 添付との対応、暗号化したメタデータ | 添付の表示 | メッセージの削除に連動して消える | 同上 |
| `attachment_uploads` | アップロードの管理情報 (オブジェクトキー、サイズ、状態) | 不正な差し替えの検出、掃除 | 行は消えない。`purged_at` を立てるだけ | purge の 7 日後に削除 |

### 3.3 本人確認とセッション

| テーブル | 主な中身 | 必要な理由 | 今の保持 | 目標 |
|---|---|---|---|---|
| `users`、`user_identities` | 本人確認の識別子の SHA-256 (World ID なら nullifier のハッシュ)、`verification_level`、表示名。nullifier の生値は持たない (docs/30、2026-11-07) | 一人一アカウントの保証 | 本人の操作で即時に削除できる (2026-11-07) | 現状どおり |
| `sessions` | セッション ID、JWT ID、発行・期限・失効の時刻 | ログアウト後の無効化 | 消えない。有効期限の 14 日を過ぎても残る | 期限切れの 1 日後に削除。失効したものも有効期限までは残す (ログアウトした JWT を拒むのに行が要る) |
| `replay_nonces` | 認証・送信・DPoP の再送防止キー | 再送攻撃の防止 | 2〜5 分。60 秒ごとに掃除している | 現状どおり |

### 3.4 利用者が作った設定

| テーブル | 主な中身 | 今の保持 | 目標 |
|---|---|---|---|
| `agents`、`agent_identities` | ラベル、DID、公開鍵、自動返信のスイッチ | 利用者が消すまで | 現状どおり。アカウント削除で消える |
| `agent_device_lists` | エージェントを作ったブラウザの鍵が署名した、読める端末の一覧 (各端末の DID と X25519 公開鍵と種類)。版ごとに残す (2026-11-12、docs/40) | エージェントを消すまで | 現状どおり。中身は `agent_identity_keys` と同じ公開情報。アカウント削除で消える |
| `contacts`、`contact_key_wraps` | 相手の DID と、端末で封をした人名・エージェント名・メモ (`sealed`)。連絡先用の鍵は、利用者の各エージェントの公開鍵で包んだ形でだけ持つ (2026-11-07、P3-8) | 利用者が消すまで | 現状どおり。平文の列は消した (2026-11-08、migration 0022) |
| `blocks` | 相手の DID、相手の `world_id_hash` | 利用者が消すまで | 現状どおり |
| `agent_auto_reply_policies` | ポリシーの JSON (許可リストと定型文を含む) | 利用者が消すまで | 現状どおり |
| `review_keys` | AI の下書きを読むブラウザの X25519 公開鍵と、ブラウザの種類 (例: Chrome (Mac)) (2026-11-08、docs/33 §9) | 利用者が外すまで | 現状どおり。アカウント削除で消える |
| `agent_drafts` | クラウドの AI が作った下書き。宛先と確認用ブラウザの鍵で包んだ暗号文、送受信者の DID、スレッド、作った AI の名前 (MCP のクライアント名) (2026-11-08、docs/33 §9) | 送るか捨てるまで、最長 7 日 | 7 日で読めなくなり、保持ジョブで消える |
| `mcp_resources` | パソコンの MCP の URL と、どの人のどのエージェントか (2026-11-08、docs/33 §10) | クレデンシャルを消すまで | 現状どおり |
| `oauth_clients` | クラウドの AI のアプリの名前と戻り先 URL (登録したもの、またはクライアント情報の URL から取ったもの) | 誰もつながないまま 30 日で消える | 現状どおり |
| `oauth_grants`、`oauth_codes`、`oauth_tokens` | 誰がどのエージェントにどのアプリを許したか、権限、時刻。コードとトークンはハッシュだけ | 許可は切って 30 日、使わず 60 日で消える。コードとトークンは期限の 1 日後 | 現状どおり |

### 3.5 エージェントの資格情報

| テーブル | 主な中身 | 今の保持 | 目標 |
|---|---|---|---|
| `agent_credentials` | 登録用シークレットのハッシュ (有効化で消す)、公開鍵、スコープ、ポリシー | 失効後も残る。失効から 7 日以上たったものは、利用者が手動で purge できる。有効化されないまま登録期限が切れた pending も残る | 失効の 30 日後に自動で削除。期限切れの pending は 7 日後に削除 |
| `agent_tokens` | アクセス・リフレッシュトークンのハッシュ、DPoP 鍵の指紋、期限、使用回数 | 消えない | 期限切れ・失効の 7 日後に削除 |
| `agent_identity_keys` | DID と公開鍵の履歴、ローテーションの証明 | 消えない | 当面は残す。公開鍵で秘匿性は低く、`agents.did` は鍵ローテーション後も最初の DID を指すため、消すと旧 DID の解決が壊れるおそれがある |

### 3.6 監査とログ

| データ | 主な中身 | 今の保持 | 目標 |
|---|---|---|---|
| `agent_audit_log` | イベント名と `detail` の JSON。詳細は下記 | 消えない | 90 日で削除。IP とユーザーエージェントはトークン・クレデンシャル系だけに残し、ユーザーエージェントは 256 文字で切る |
| Fly のログ (API) | 送信・削除のたびの user_id とメッセージ ID、マスクした nullifier、エラーの詳細 | Fly の既定に従う (ログ検索は 7 日、ベータ機能) | 成功時の storage イベントは出さない。外部への長期転送はしない |
| メモリ上の状態 | レート制限のカウンタ (ログイン中のブラウザは user_id ごと、それ以外は IP ごと、1 分の窓)、送信者 DID ごとの連投カウンタ | 窓が終われば上書きされ、再起動で消える | 現状どおり |

`agent_audit_log` の `detail` に入るもの:
- トークン・クレデンシャル系のイベント: IP とユーザーエージェント
- 添付系のイベント: IP とユーザーエージェント
- 自動返信系のイベント: DID の組とメッセージ ID
- ポリシー変更のイベント: 変更前後の JSON 全体

### 3.7 委託先

| 委託先 | 渡しているもの | 保持 |
|---|---|---|
| Supabase (DB) | §3.2〜3.6 の全テーブル | バックアップの有無はプランによる。Free は自動バックアップなし、Pro は日次で 7 日分。行を消しても、その期間はバックアップに残る |
| Cloudflare R2 | §3.1 の暗号文 | アップロードから 97 日で消すライフサイクルルールを設定済み (2026-11-07、§5 P1) |
| Fly.io | API の実行とログ | §3.6 のとおり |
| Vercel | Web の配信。`/api/*` を API へ中継するので、通信の中身 (本文は暗号文)、Cookie、ヘッダが通る。Web Analytics (Cookie なしのページビュー) も使っている | ランタイムログは Hobby で 1 時間、Pro で 1 日 |
| World (developer.world.org) | ログイン時の IDKit の証明 (nullifier を含む) | World 側の規約による |

### 3.8 運営が持っていないもの

- 秘密鍵 (ブラウザの IndexedDB、または Signer Daemon)
- BYOK の Anthropic API キーと Google Calendar のトークン。ブラウザの IndexedDB にあり、ブラウザから直接呼ぶ
- ブリッジのトークン (ブラウザに暗号化して保存)
- Gateway と Signer Daemon のログ (利用者のマシン)

## 4. 保持期限 (決定案)

| データ | 期限 | 削除のしかた |
|---|---|---|
| 本文と添付の暗号文 | 作成から 90 日 | API の保持ジョブ (日次)。最後の網として、R2 のライフサイクルルール (97 日) も併用する |
| `message_index` / `message_attachments` | 本文と同時 | 保持ジョブ。墓標は残さない |
| `attachment_uploads` (purge 済み) | purge の 7 日後 | 保持ジョブ |
| `sessions` | 期限切れの 1 日後 (失効済みも有効期限までは残す) | 保持ジョブ |
| `agent_tokens` | 期限切れ・失効の 7 日後 | 保持ジョブ |
| `agent_credentials` (失効済み) | 失効の 30 日後 | 保持ジョブ。トークンは外部キーで連鎖して消える |
| `agent_credentials` (登録期限切れの pending) | 期限切れの 7 日後 | 保持ジョブ |
| `agent_audit_log` | 90 日 | 保持ジョブ |
| `agent_drafts` | 作成から 7 日 (送る・捨てるとその場で消える) | 保持ジョブ (2026-11-08) |
| OAuth (`oauth_*`) | コード・トークンは期限の 1 日後。許可は切って 30 日、使わず 60 日。登録だけのアプリは 30 日 | 保持ジョブ (2026-11-08) |
| `users` と利用者の設定 | アカウント削除まで | 本人の操作で削除 (§5 P2) |
| `replay_nonces` | 2〜5 分 | 既存の掃除 (60 秒ごと) |

90 日にする根拠は 2 つある。
- エージェント間のやり取り (日程調整や依頼) を追うには十分な長さである
- 受信用の鍵が後で漏れても、読まれうる範囲を直近 90 日分に限れる

## 5. 対応の順番

### P1 (先にやる)

進み具合 (2026-11-07):
- 保持ジョブを実装した。`AGENT_INBOX_RETENTION_MODE` が `enforce` でない限り、消す件数をログに出すだけ (`off` / `dry_run` / `enforce`)。本番は `dry_run` で出し、件数を確かめてから `enforce` に切り替える
- プライバシーポリシーを直した: 本文と添付の保存場所 (R2)、監査ログに IP とユーザーエージェントが入ること、委託先。90 日の保持は `enforce` に切り替えるときに書き足す
- アカウント削除の手作業 (18a §11.1) を直した
- 2026-11-07 に `enforce` に切り替えた。切り替える前に dry_run で消す件数を確かめ、承認を得た (errors 0、2 回の実行で同じ件数)
- 同じ日に、プライバシーポリシーに 90 日の保持を書き足した
- R2 のライフサイクルルールを設定した (2026-11-07、wrangler)。内容は次のとおり
  - ルール名: `retention-97-days`
  - 対象: 全プレフィックス
  - アップロードから 97 日で削除
- 最初の enforce 実行 (2026-11-07 08:42 UTC 頃) は、dry_run と同じ件数を消した。errors 0
- 旧自動パージ (`/admin/purge/run`) を削除した。エンジン、エンドポイント、テストを消し、`/status` の `auto_purge_enabled` は `retention_mode` に置き換えた (2026-11-07)
- P2 の 5 と 6 を済ませた (2026-11-07)
  - 監査ログの IP とユーザーエージェントは、トークン・クレデンシャル系と、レート制限で拒否したイベントだけに残す。添付の通常の操作 (作成・完了・添付・ダウンロード URL・削除) からは外した
  - ユーザーエージェントは 256 文字で切る (`audit_user_agent`)
  - storage イベントは失敗したときだけログに出す
  - プライバシーポリシーの監査ログの説明も、これに合わせた

1. **R2 のライフサイクルルール**: 本文と添付のプレフィックスに、97 日で消えるルールを設定する。アプリでの削除が失敗して孤立した本文も、ここで消える。
2. **API の保持ジョブ**: 日次の保持ジョブを足す。添付の掃除と同じく、プロセス内で定期的に実行する。中身は §4 の表をそのまま実装したものにする。今の自動パージ (`/admin/purge/run`) は本番で無効のまま残っているので、`enforce` に切り替えた後で削除する。
3. **プライバシーポリシーの修正**: 保持期間と本文の保存場所の記述を、実態に合わせて直す (§6)。

### P2

4. **本人によるアカウント削除 (済、2026-11-07)**: `DELETE /auth/account` を作り、設定画面のプロフィールから使えるようにした。
   - World ID で 10 分以内にログインしたセッションに限る
   - 相手方が参照している本文と添付は残し、共有している添付は相手に移す
   - プライバシーポリシーも、本人が削除できる旨に直した
5. **監査ログの絞り込み**: IP とユーザーエージェントを残すイベントを絞る (§3.6)。
6. **Fly のログの整理**: 成功時の storage イベントを出さないようにする。
7. **受信箱での告知と保存手段**: 「90 日で消える」ことを受信箱に表示し、残したいメッセージを利用者側に保存する手段を用意する。
   - 告知は済ませた (2026-11-07)。受信箱の一覧の上に表示し、閉じた状態はそのブラウザで覚える
   - 保存手段も済ませた (2026-11-07)。会話画面の「このスレッドを保存」で、このブラウザが復号した内容をテキストファイルとして保存する。ファイル名に件名は入れない

### P3

8. **連絡先の暗号化 (済、2026-11-07)**: 連絡先の人名とメモを利用者側で暗号化する。サーバは評価に要る DID だけを平文で持つ。
   - 人名・エージェント名・メモは端末で AES-GCM の封をして `contacts.sealed` に置く (`cs1:`)。相手の DID を AAD に入れるので、サーバが封を別の DID の行へ付け替えても開けない
   - 連絡先用の鍵は利用者ごとに 1 本。利用者の各エージェントの X25519 公開鍵で包んで `contact_key_wraps` に置く (`ckx25519v1:`)。HKDF の info はメッセージ用と分けたので、メッセージの包んだ鍵を連絡先の鍵として開くことはできない
   - エージェントの鍵を持つ端末なら開ける。最初の鍵は、エージェントの鍵を持つ端末だけが作る。2 台が同時に作ろうとしたら、後の 1 台は 409 を受けて先の鍵を開く。開けた端末は、包んだ鍵が無いエージェントの分を足す
   - どの端末でも開けなくなったら、連絡先ページで鍵を作り直せる (`DELETE /contact-keys`)。今ある連絡先の名前は読めなくなるが、削除はできる
   - 封をする前の行は無かった (2026-11-07 に本番で 0 件を確認)。平文の列 (`person_name`、`agent_label`、`note`) は migration 0022 で消し、`sealed` を必須にした。名前やメモを平文で書ける列は、もう無い
   - 信頼の前提: エージェントの公開鍵はサーバから受け取る (送信時に宛先の公開鍵を受け取るのと同じ)。DB の漏洩や運営に読まれることは防ぐが、鍵をすり替えるサーバは防がない
9. **添付から user_id を外す (済、2026-11-07)**: 添付のオブジェクトキーと S3 メタデータから user_id を外す。
   - キーは `attachments/<attachment_id>/blob.bin`。下書き ID も外した (どの添付が同じメッセージのものかも、キーの一覧からは分からない)
   - 署名付き PUT に縛るメタデータは `attachment-id` と `issued-at` だけ。持ち主は `attachment_uploads.owner_user_id` にだけある
   - 以前のオブジェクトは古いキーとメタデータのまま残り、R2 の 97 日のルールで消える。照合は `attachment-id` とサイズだけなので、古いオブジェクトもそのまま使える
10. **nullifier の置き場所を減らす (済、2026-11-07)**: 目標より進めて、生値はどこにも置かないようにした。`users.nullifier_hash` は空にし、以後は書かない。JWT の `wid` と再送防止のキーもハッシュにした (docs/30)。

## 6. 実態とずれている記述と手順

- **プライバシーポリシー**: `apps/web/lib/i18n/locales/{ja,en}.json` の `retentionBody` には「E2E 暗号化された本文はご自身のストレージ (BYOS) にあり、サーバ上のアカウント削除の影響を受けない」とある。しかし本番では、本文の暗号文は運営の R2 にある。アカウント削除の手作業 (18a §11.1) でも消している。記述を実態に合わせる。
- **アカウント削除の手作業 (18a §11.1)**:
  - R2 にある添付の本体が手順に入っていない。DB の行は外部キーで連鎖して消えるが、R2 には残る。
  - 「storage_ref を拾って R2 から削除」とあるが、このままだと相手の受信箱と共有している本文まで消してしまう。メッセージ削除と同じく、ほかの行が参照していない本文だけを消す。
- **紹介文と用語集 (済、2026-11-07)**: BYOS と読める表現を外し、「鍵は利用者だけが持つ・暗号文は運営の保存先 (R2) に 90 日」に統一した。対象は紹介文 (`whatBody`、ラベルは `pillKeys` に改名)、使い方の手順 3 と用語集 (`storageTerm` / `storageDesc`)、「インデックスは暗号化メタデータのみ」と言い過ぎていた `zkDesc`、利用規約 (`terms.contentBody`)、ログイン画面のフッター (`footerIdentity`)、OG 画像、連携画面の保存先の表示、README
- **docs/06 の Auto-Purge**: これは容量管理のための設計で、AI 分類と未読日数を条件にしている。§4 の保持期限はプライバシーのための上限で、目的が違う。保持ジョブが入ったら、06 にその旨を注記する。
