# 30. ADR: 一意の人間を土台にした、差し替えられる本人確認

**Status**: Accepted (2026-11-07)
**Related**: [03 認証・ID](./03_identity_auth.md)、[05 ブロック](./05_security_filtering.md)、[28 保持期限](./28_data_inventory_and_retention.md)
**Scope**: 本人確認の証明手段を差し替えられるデータモデルとログインの流れ、人間単位の上限、人間単位のブロックの照合。新しい証明手段そのもの (パスポートなど) の追加は範囲外。

## 1. 背景

2026-11-07 に、次の方針を決めた。

- 本人確認の土台は「一意の人間」であることにする
- 証明手段 (今は World ID の Orb) は、将来差し替えられる作りにする

利用者はまだ運営者だけなので、データの移行や告知が要る変更は今のうちに入れる。

## 2. 現状 (2026-11-07 確認)

**World ID 専用の作りになっている:**

- `users` に `nullifier_hash` (World ID の生の値、UNIQUE、NOT NULL) と `world_id_hash` (その SHA-256、UNIQUE、NOT NULL) がある
- ほかの証明手段で入ってきた人を表せない

**生の nullifier が残る場所がある:**

- `users.nullifier_hash`
- セッション JWT の `wid`
- 再送防止のキー

**上限がエージェント単位にしかない:**

- 送信上限は資格情報単位で、1 日 200 通 (L3)
- 1 人が作れるエージェント数にも、上限がない
- そのため、エージェントや資格情報を増やすほど、1 人で送れる量も増える

**不具合: 人間単位のブロックが、ブラウザからの送信に効いていない:**

- ブロック (`l2_identity` / `l3_stealth`) は、相手の `world_id_hash` で記録している (`create_block_from_message`)
- `send_message` は、照合に使う値を送信元によって変えていた
  - agent トークンからの送信: `users.world_id_hash` (ハッシュ) と照合する
  - ブラウザのセッションからの送信: JWT の `wid` (生の nullifier) と照合する
- ハッシュと生の値は一致しないので、ブロックした相手でも、ブラウザから送れば届いていた

## 3. 決定

### 3.1 証明手段の条件と強さ

差し替えに使える証明手段は、次の 3 つを満たすものに限る。

1. 同じ人には、このサービスで常に同じ識別子が返る
2. 運営に氏名・住所・生体データなどの個人情報が渡らない
3. 暗号的に検証できる

パスキーは、同じ人がいくつでも作れて 1 を満たさないので、本人確認には使わない (ログイン手段にとどめる)。

証明手段ごとに、強さ (`assurance`) を付ける。

| assurance | 意味 | 例 |
|---|---|---|
| `high` | 生体による一意性 | World ID の Orb (今の唯一の手段) |
| `medium` | 公的な書類 1 冊につき 1 つ | IC チップ付きパスポートのゼロ知識証明 (将来) |

### 3.2 データモデル

新しいテーブル `user_identities` を足す (migration 0020)。

| 列 | 中身 |
|---|---|
| `user_id` | 持ち主 (`users.id`、削除は連鎖) |
| `provider` | 証明手段 (`world_id` など) |
| `subject_hash` | 証明手段がくれる識別子のハッシュ。base64url(SHA-256(識別子))。生の値は保存しない |
| `assurance` | 3.1 の強さ |
| `created_at` / `last_verified_at` | 登録と最後の確認の時刻 |

制約と運用:

- `UNIQUE (provider, subject_hash)` で「1 つの証明 = 1 つのアカウント」を保証する
- 1 人が複数の証明手段を持つことはできる (同じアカウントに足す)

World ID の `subject_hash` は、既存の `world_id_hash` と同じ式にする。既存のブロックの記録をそのまま使えるようにするため。

`users` 側の変更:

- `nullifier_hash`: NOT NULL を外して、既存の値を消す。以後は書かない
- `world_id_hash`: NOT NULL を外す (World ID 以外の手段で入った人には無い)。World ID の利用者には今までどおり入れる (ブロック照合と信頼スコアが使う)

セッション JWT の `wid` と再送防止のキーには、生の nullifier ではなくハッシュを入れる。

### 3.3 ログインの流れ

1. 証明手段ごとの検証 (今は World ID v4) が、「確認された人 (provider, subject_hash, assurance)」を返す
2. 共通の処理 (`resolve_or_create_user`) が、1 つのトランザクションで次を行う
   - 同じ人の同時ログインを advisory lock でそろえる
   - `user_identities` を引く
   - 見つかればそのアカウントを返し、確認時刻と強さを更新する
   - 無ければ `users` と `user_identities` を作る
3. セッションを発行する

新しい証明手段を足すときは、1 の検証を足すだけにする。2 と 3 は共通のまま使う。

### 3.4 人間単位の上限

**送信:**

- 1 人 1 日あたりの送信数に上限を掛ける
  - 既定は 500 通 (`AGENT_INBOX_SEND_LIMIT_PER_HUMAN_PER_DAY`)
  - 人間のセッションからの送信と、すべてのエージェントからの送信を合算する
  - 上限を超えたら 429 を返す
- 数は `user_send_counters (user_id, day)` に、条件付きの INSERT ... ON CONFLICT で原子的に足す
  - 利用者が送信済みを消しても、数は減らない
  - 拒否した送信も数に入る (試行の上限)
- 資格情報単位の L3 (1 日 200 通) は残す

**エージェント数:**

- 1 人が持てるエージェント数に上限を掛ける
  - 既定は 20 (`AGENT_INBOX_MAX_AGENTS_PER_HUMAN`)
  - 上限を超えたら 409 を返す
- エージェントの作成は 1 つのトランザクションにまとめる
  - 持ち主の行をロックしてから数えるので、同時作成でも上限を超えない
  - 途中で失敗して、身元の行が無いエージェントが残ることもなくなる

`user_send_counters` は、保持ジョブが 2 日より古い行を消す。

### 3.5 人間単位のブロック

`send_message` は、送信元が人間のセッションでも agent トークンでも、DB の `users.world_id_hash` で照合する。2 の不具合はこれで直る。

DB を使わない開発モードだけは、JWT の `wid` を使う。この `wid` も 3.2 でハッシュになっているので、照合の値は同じ形にそろう。

将来 World ID 以外の手段が入ったら、ブロックは「相手のすべての identity」で照合するように広げる。

### 3.6 証明手段をまたいだ重複

同じ人が、証明手段ごとに別のアカウントを作れてしまう。これは仕組み上防げない (手段どうしで共通の識別子が無い)。そこで次のようにする。

- 上限は「証明 1 つにつき 1 アカウント」の単位で掛かる。これで、手段の数を超えて増やすことはできない
- 将来は、受信側のポリシーで「`high` の人だけ」と指定できる条件を足す (`min_assurance`)

## 4. 移行

利用者がいないので、migration 0020 の中で次の 2 つを行う。

- 既存の行から `user_identities` を作る
- 生の nullifier を消す

運営者のアカウントは、次のログインで同じ `subject_hash` から見つかる。古いセッション JWT は `wid` に生の値を持つが、DB があるときの照合にはもう使わない。

## 5. テスト

- 同じ証明で 2 回ログインしても、アカウントも identity も 1 つで、`users.nullifier_hash` が空であること
- 人間単位でブロックされた人が、ブラウザのセッションから送ると 404 になること (2 の不具合の回帰テスト)
- 1 日の送信上限を超えると 429 になること。エージェントを増やしても合算されること
- エージェント数の上限を超えると 409 になること

## 6. 範囲外

- 新しい証明手段の追加 (パスポートのゼロ知識証明、マイナンバーカードなど)
- 既存のアカウントに証明手段を足す UI
- ポリシーの `min_assurance` 条件
- ブロックを `user_identities` 単位に広げること (3.5)
