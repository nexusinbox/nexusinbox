# 31. 使い始めの体験（オンボーディング）を簡単にする

**Status**: 課題の記録と方針 (2026-11-08)。§4 の 1 と 2 は実装済み (§5)。今後の優先事項
**Scope**: 初めて使う人が、エージェントを作って、必要なら自分のマシンのデーモンにつなぎ、自動返信まで動かすまでの体験
**Related**: [19 非対話型アクセス runbook](./19_non_interactive_agent_runbook_2026-04-18.md)、[21 MCP モード別の可視性](./21_message_visibility_ux_for_mcp_modes.md)、[29 Isolated モードの自動返信](./29_isolated_auto_reply_recovery.md)

## 1. 背景

2026-11-08 に、本番で利用者側ノード（signer daemon と Gateway）を最初から通した。仕組みとしては動いたが、運営者自身が操作して「とても使いづらい」と感じた。

ユーザーの言葉:「UIUX がとても使いづらいと思った。オンボーディング的に使い始めの最初の設定だとしても、もっと簡単にシンプルにわかりやすくする必要がある」

利用者がまだいない今のうちに、最初の体験を作り直す。機能を足す前に、ここを優先する。

## 2. 検証で詰まった点（2026-11-08）

1. **既存のエージェントにデーモンをつなぐと、宛先の鍵が移る**: 新しく有効にした鍵が宛先になるので、今の読み方（ペアリング済みのデーモン経由）が崩れる。それを避けるために、検証用のエージェントを別に作る必要があった。仕組みを知らないと気づけない
2. **Web とターミナルを行き来する手順が多い**: credential を作り、ID だけを伝え、1 回しか表示されないシークレット（30 分で失効）をターミナルに貼り、パスフレーズを 2 回入力する
3. **起動コマンドが長い**: 環境変数 10 個（API の URL、AID、credential ID、鍵ファイル 2 つ、ランタイムディレクトリ、ソケット 2 つ、自動返信の設定 2 つ）を並べた 1 行
4. **パスフレーズの入力が壊れやすい**: 入力前にタブを閉じると、空のパスフレーズのまま起動が進み、Gateway だけが残った（起動スクリプトは修正済み）
5. **自動返信の設定が分かれていて用語が難しい**: 「自動返信を有効にする」「デフォルトアクション」「プロトコルで上書き」など、別々の操作と専門用語が要る
6. **宛先の指定が分かりにくい**: 名前を入れると「受信者の暗号化鍵が見つかりません。」とだけ出る。候補から選ぶと、デーモンが開けない鍵が使われた（宛先は AID で解決するよう修正済み）
7. **エージェントの設定画面が長く、技術的すぎる**: 鍵の所在、Signer Daemon Bridge（ADVANCED・DEV）、Interactive / Isolated / Autonomous、DID と AID、credential が一画面に並ぶ
8. **動いているかが画面で分からない**: デーモンがつながったか、自動返信が送られたかは、ログを読んで確かめるしかなかった
9. **概念が多すぎる**: aid、did:key、credential、登録用シークレット、鍵の保管場所、Bridge、Gateway、executor、ポリシー

## 3. 方針

- **一本道のガイドにする**: 「エージェントを作る → どこで動かすかを選ぶ（このブラウザだけ / 自分のマシン）→ 自分のマシンなら 1 コマンドを実行 → 画面に『接続しました』と出る → よく使う設定をプリセットで選ぶ → 自分宛てにテストを送る」を、迷わず進めるようにする
- **識別子と専門用語は表に出さない**: 普段は名前で示す。DID・AID・credential は「詳細」の中に入れる
- **シークレットを手でコピーさせない**: 登録はペアリングの形（画面とデーモンで短いコードを照合する等）に寄せ、1 回しか表示されない値を人が運ぶ手順をなくす。安全性は今と同等以上に保つ
- **状態を画面で見せる**: デーモンの接続状態（最後に接続した時刻）、自動返信が最後に何をしたかを、エージェントの画面に出す
- **既定値で動く**: 起動に必要な値は登録時に保存し、起動のたびに並べさせない
- **壊れにくくする**: 途中で止まったら、何をすれば戻せるかを画面とコマンドの出力で伝える

## 4. 進め方

1. **すぐ効く簡素化（エンジニアリング）**: `--enroll` が設定をディレクトリに保存し、起動・停止はそのディレクトリを指定するだけにする。Web の登録コマンドも短くする
2. **画面の流れの設計**: 一本道のガイドの画面案を作り、運営者に見てもらってから実装する
3. **状態の表示**: デーモンの接続状態と、自動返信の直近の動きを、エージェントの画面に出す
4. **設定の整理**: エージェントの設定画面を「よく使う設定」と「詳細」に分け、自動返信はプリセットで選べるようにする

## 5. 実装 (2026-11-08)

画面案 ([31_onboarding_mock.html](./31_onboarding_mock.html)) を運営者に見てもらい、その流れで実装した。

### 5.1 はじめての設定 (`/onboarding`)

1. **名前**: エージェントを作る (鍵はこのブラウザで作る。設定画面の作成と同じ処理)
2. **どこで動かすか**: 「このブラウザだけ」(既定) か「自分のパソコンでも動かす」
3. **パソコンとつなぐ** (選んだときだけ): 接続コードとコマンドを出し、credential が有効になるまで 2 秒ごとに確かめる。つながると「接続しました（macOS）」に切り替わる
4. **届いた依頼への対応**: 3 つから選ぶ (§5.3)
5. **テスト**: 自分の AID 宛てに日程調整の依頼を 1 通送り、届いたこと、設定どおりの判定、パソコンなら自動の返事まで画面で見せる
6. **完了**: このエージェントの受信箱へ

サイドバーの「エージェントを作成」と、エージェントがまだないときの受信箱の案内から入る。作成後は URL に agent ID を持つので、再読み込みしても別のエージェントを作らない。

### 5.2 接続コード

- `POST /agent-credentials` に `pairing: true` を付けると、`ens_` シークレットの代わりに 10 文字のコード (Crockford base32、50 ビット、`XXXXX-XXXXX`) を返す。有効期限は 10 分で、保存するのは正規化したコードの SHA-256 だけ
- `POST /agent-pairing/resolve` (認証なし、何も変えない) でコードから credential を引く。IP ごとに 10 分 10 回まで (形式違いも数える)
- activate はコードを入力どおりに受け付ける (大文字小文字・ハイフン・空白を無視し、O を 0、I と L を 1 と読む)。試行回数の上限 (5 回で失効) と、鍵の所持証明はこれまでどおり効く
- `device_label` を送ると credential の名前になる。daemon は OS 名だけを送る (ホスト名には利用者の名前が入っていることが多い。運営が持つデータを減らす方針)
- コードはコマンドラインに載る (シェルの履歴、プロセス一覧)。1 回限り・10 分で失効なので許容した。`ens_` シークレットは引き続きコマンドラインでは受け付けない

### 5.3 自動返信のプリセット

サーバはメッセージを読めないので、届いた時点で判定できるのは既定の動作 (`default_action` と `default_conditions`) だけ。プロトコルごとの指定は、本文を開いたパソコン (Gateway) かブラウザが見る。どちらも、サーバが auto_accept と判定した行しか拾わない。そこでプリセットは次のポリシーにした。

| プリセット | 自動返信 | ポリシー |
|---|---|---|
| まず私が確認する | オフ | 変えない |
| 連絡先からの日程調整は自動で承諾 | オン | 既定 auto_accept + `default_conditions.require_contact`、タスク依頼は queue_for_human |
| 日程調整は自動で承諾 | オン | 既定 auto_accept、タスク依頼は queue_for_human |

- 設定画面の自動返信エディタは `default_conditions` を編集しないが、保存時に保つようにした。以前は保存のたびに落ちていたので、「連絡先のみ」が黙って「誰からでも」に広がるところだった
- 承諾は候補の最初の時間で返す (既存の executor の動き)

### 5.4 画面案から変えた点

- 「パソコンでも動かす」の説明に 1 行足した: つないだあとは本文をパソコン側で開き、このブラウザでは届いたことと状態だけが見える。新しい鍵が宛先になるため (§2 の 1)
- 「接続しました」に出す名前はホスト名ではなく OS 名にした (§5.2)
- 「承認待ちに入ります」は「返事はあなたが決めます」にした。手動の依頼は承認待ちフォルダではなく受信箱に入るため
- ブラウザでの自動返信は、このエージェントの受信箱 (エージェント別) を開いている間に動く。完了画面の「受信箱へ」はそこを開く
- 完了画面の「パソコン: 接続中」「自動返信: 最後の対応」の表示は、§4 の 3 (状態の表示) で作るまで載せない

### 5.5 まだ残っていること

- §4 の 3: 接続状態と自動返信の直近の動きを、エージェントの画面に出す
- §4 の 4: 設定画面を「よく使う設定」と「詳細」に分ける
- 配布: 今の `connect` はリポジトリのフォルダで実行する前提 (Rust でビルドする)。インストール方法 (Homebrew など) を決める
- 受信箱の「自動返信」表示は、返事を送らずに処理済みにした行にも出る (パソコンの Gateway が見送ったタスク依頼、依頼ではない A2A メッセージなど)。返事を送った行だけに出すよう直す
