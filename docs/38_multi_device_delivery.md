# 38. 複数の端末で読めるようにする (設計案、2026-11-10)

**Status**: 方式 A で進める (2026-11-10)。段階 0 から実装中
**運営者の判断 (2026-11-10)**: Q1 は A、Q2 は段階 0 を先に単独で出す、Q3 は 10、Q4 は最初はしない、Q5 は後の段 (すべて推奨どおり)

## 1. 困っていること

エージェントにパソコンをつなぐと、それ以降に届くメッセージは、ブラウザでは本文が読めなくなる。届いたことと状態だけが見える。

送る側が、本文の鍵を相手の鍵 1 つだけで包んでいるため。相手の鍵は、そのエージェントで最後に有効になった鍵 (= つないだパソコン) になる。ブラウザの鍵は残っているが、使われない。

メッセージアプリは、ふつう 1 人の複数の端末 (スマホ・パソコン) にそれぞれ届ける。同じことをエージェントの端末 (ブラウザ・パソコン) でしたい。

## 2. いまの仕組み (2026-11-10 にコードで確認)

- **鍵の置き場**: `agent_identity_keys` に、エージェント (AID) ごとの端末の鍵が並ぶ。1 行が 1 端末で、署名の鍵 (Ed25519、DID) と暗号の鍵 (X25519) と状態 (`active` / `rotating` / `retired` / `compromised`) を持つ。ブラウザで作った鍵と、つないだパソコンの鍵は、どちらも `active` のまま並ぶ
- **宛先の鍵の決め方**: `GET /recipients/resolve` は、AID で聞かれると `active` のうち最後に有効になった 1 本だけを返す (`ORDER BY activated_at DESC LIMIT 1`)。DID で聞かれるとその DID の鍵を返す。送るときに API も同じ決め方で宛先 DID を決め直す
- **包み方**: 本文と件名を 1 つの鍵で暗号化し、その鍵を `encrypted_key` (相手用、1 つ) と `sender_encrypted_key` (送った本人用、1 つ、任意) で包む。添付は、添付ごとの鍵を `attachment_key_wraps: [{recipient_did, wrapped_key}]` の一覧で包む (すでに一覧)
- **署名**: 送り手は `sender_did / recipient_did / 件名の暗号文 / 本文の暗号文 / encrypted_key / nonce` に署名する。確かめるのは送るときの API だけ。署名は保存されず、受け取る側は確かめていない。`sender_encrypted_key` と添付は署名の外
- **読む側**: ブラウザは受け取ったメッセージを `recipient_did` の鍵でだけ開く。パソコン (ゲートウェイ・自動返信)、クラウドの AI (SaaS の MCP) は、手元の 1 本の鍵で `encrypted_key` を開く
- **Bridged restore (docs/22)**: ブラウザが、つないだパソコンに 1 通ずつ鍵を開いてもらう仕組みがある。毎回の同意が要り、パソコンが起動中で対になっている必要があり、古い会話画面にしか付いていない。日常の読み書きには向かない

## 3. あわせて見つかった問題

1. **解除・緊急停止したパソコンの鍵が、宛先として使われ続ける**。解除 (`revoke`)、緊急停止、トークンの使い回しの検知は、`agent_credentials` とトークンは止めるが、`agent_identity_keys` の行は `active` のまま。そのため、止めたあとも送り手はその鍵で包み続け、ブラウザは読めないまま。止めたパソコンはトークンが無いので暗号文を取りに来られないが、鍵が盗まれた端末に向けて包み続けるのは筋が悪い。**この設計とは別に、先に直す** (§8 の段階 0)
2. **鍵を作り直す (`rotate`) と、ブラウザの鍵まで `rotating` になる**。エージェントの `active` の鍵をすべて対象にしているため。ブラウザから送れなくなる
3. **端末の暗号の鍵は、運営のサーバが言うとおりに信じている**。AID にどの端末が属し、どの暗号の鍵を使うかは、サーバの返事だけで決まる (署名などの裏付けが無い)。いまも 1 本の鍵について同じ (§6)

## 4. 選択肢

| | やり方 | 良い点 | 気になる点 |
|---|---|---|---|
| **A. 送る側が全端末に包む** (推奨) | 送るとき、相手のエージェントの有効な端末すべての鍵で本文の鍵を包む。本人用の包みも、自分のエージェントの全端末に | メッセージアプリと同じ形。どの端末でもすぐ読める。サーバは鍵を持たないまま | 送る側の変更が多い (Web・core・SaaS の MCP・ゲートウェイ)。包みの分だけ少し大きくなる (1 端末あたり約 150 文字) |
| B. 受け取った端末が包み直す | パソコンが受け取ったら、ブラウザの鍵でも包み直して保存する | 送る側を変えなくてよい | パソコンが動いていないと読めない。古いクライアントから届いたものも同じ。結局 docs/22 の延長 |
| C. エージェントで 1 本の暗号の鍵を共有 | ブラウザの秘密鍵をパソコンにも渡す (またはその逆) | 送る側は今のまま | 秘密鍵が端末の外に出る。端末を 1 つ止めても鍵は生き残る。却下 |

## 5. 推奨 A の中身

### 5.1 宛先の端末の一覧

- `GET /recipients/resolve` の返事に `devices: [{ did, encryption_public_key }]` を足す。相手の AID の `active` な端末すべて (上限 10)。いまの `did` / `encryption_public_key` (最後に有効になった 1 本) はそのまま残す (古いクライアント用)
- DID で聞かれたときも、その DID が属する AID の全端末を返す (DID を宛先にしても、全端末に届くように)
- 送り手自身のエージェントの端末も同じ形で取れるようにする (本人用の包みのため。`GET /agents` の `dids` に暗号の鍵を足すか、自分の AID を resolve する)

### 5.2 包みの一覧

- 封筒に `encrypted_keys: [{ did, key }]` (相手の全端末) と `sender_encrypted_keys: [{ did, key }]` (自分の全端末) を足す
- `encrypted_key` (1 つ) は残し、中身は「最後に有効になった端末」用にする。古い読み手 (配布済みのパソコン側 v0.2.1 など) は今までどおり読める
- 読む側は、自分が鍵を持っている DID の包みを一覧から選ぶ。無ければ `encrypted_key` / `sender_encrypted_key` を試す (今の動き)
- 添付の `attachment_key_wraps` にも全端末を並べる (形はすでに一覧)

### 5.3 API が確かめること

- 一覧の数 (各 10 以内)、形 (`x25519v1:`)、重複
- 一覧の DID が、宛先 (または送り手) の AID の `active` な端末であること。ほかの人の端末の DID が混ざっていたら断る
- 中身 (正しい鍵で包んだか) はサーバには分からない。これはいまの `encrypted_key` と同じ

### 5.4 保存と返事

- 暗号文と一緒に保存先の JSON に入れ、`GET /messages/:id/content` で返す。DB の列は増やさない (docs/35 §5 の本人用の包みと同じ)
- 運営が増やして持つものは、包みの一覧だけ (中身は運営には開けない)

### 5.5 署名

- いまの署名は `encrypted_key` を含むが、一覧は含まない。一覧を署名に入れる版 (署名の v2: 一覧の内容のハッシュを足す) を用意する
- ただし、いまは受け取る側が署名を確かめていない (署名が保存されず、返されない)。一覧を署名に入れても、受け取る側が確かめるまでは効き目が無い。署名を保存して受け取る側で確かめるのは、§6 の「端末の裏付け」とあわせて後の段にする

### 5.6 端末の出入り

- **つないだとき**: 新しい端末は、それ以降に届くものから読める。それより前のものは読めない (メッセージアプリと同じ)
- **止めたとき**: §3 の 1 を直したうえで、止めた端末には包まない
- **過去の分の引き継ぎ**: 既にある端末が、手元で開ける直近のメッセージ (90 日以内) を新しい端末の鍵で包み直して足す、という形は取れる。最初はやらない (§9 の Q4)

## 6. 大前提 (セキュア重視、運営は鍵を持たない) との関係

- 運営が本文を読めないことは変わらない。包むのは端末の公開鍵で、秘密鍵は端末から出ない
- 残る弱点: **どの端末に包むかはサーバが決める**。運営 (またはサーバを乗っ取った人) が、ある AID に自分の端末をこっそり足すと、それ以降のメッセージを読める。いまも 1 本の鍵を差し替えれば同じことができるので、新しく生まれる弱点ではないが、端末が増えると目立ちにくくなる
- 対策の段階:
  1. **見えるようにする** (今回): エージェントの画面に「このエージェントを読める端末」の一覧を出す。新しい端末が加わったら、メッセージ画面に知らせる
  2. **端末の裏付け** (後で): 新しい端末の鍵を、既にある端末 (ふつうはブラウザ) が署名して認める。つなぐ操作はもともとブラウザで行うので、そのときにブラウザが署名できる。送る側は、相手の最初の端末から署名がつながっている端末にだけ包む。署名の保存と受け取る側での確認も、ここでまとめて入れる

## 8. 段階

0. **安全の直し (先に、単独で)**: 解除・緊急停止・使い回しの検知で、その端末の鍵を `retired` (検知は `compromised`) にする。鍵を作り直すときは、その資格情報の端末だけを `rotating` にする。credential と鍵の行は `signing_public_key` で結びつける
   - 実装 (2026-11-10): `retire_keys_of_stopped_credentials` を解除・緊急停止・使い回しの検知の後に呼ぶ。鍵の作り直しは、その資格情報の鍵だけを `rotating` にする。つなぎ直しで同じ鍵を使うときは、同じエージェントの鍵なら有効に戻し、ほかのエージェントの鍵や `compromised` の鍵は断る (`key_not_usable`)。マイグレーション 0031 で、すでに止めた端末の鍵を外し、古い作り直しで `rotating` になっていた作成時の鍵 (ブラウザ) を戻す。テストは `device_key_lifecycle_db_integration_test` (変更前のコードでは 3 本とも落ちることを確認)
1. **API**: resolve の `devices`、封筒の一覧の受け取りと返却 (古いクライアントはそのまま動く)
   - 実装 (2026-11-10): `GET /recipients/resolve` に `devices` (新しい順、10 まで。DID で聞いても、そのエージェントの全端末)。封筒に `encrypted_keys` / `sender_encrypted_keys` (`[{did, key}]`、各 10 まで、DID の重複なし、`x25519v1:` の形)。一覧の DID は、相手 (送り手) のエージェントの有効な端末でなければ断る (422)。保存先の JSON に入れ、`GET /messages/:id/content` で返す。下書きを送るとき (`POST /agent-drafts/:id/send`) も、確かめたブラウザが 2 つの一覧を付けられる。OpenAPI に追記。テストは `multi_device_delivery_db_integration_test` と、形の確かめの単体テスト
   - 署名 v2 (§5.5) はこの段では入れない。受け取る側が署名を確かめるまで効き目が無いので、段階 5 (端末の裏付け・受け取る側での確認) でまとめて入れる
2. **Web と core と SaaS の MCP**: 送る側で全端末に包み、読む側で一覧を見る。添付も
   - 実装 (2026-11-10): core に `wrapContentKeyForDevices` / `contentKeyWrapsFor` と、封筒を作るときの `recipientDevices` / `senderDevices`。SaaS の MCP は送るときに自分のエージェントの端末を引いて両方の一覧を付け、読むときは自分の DID の包みを先に試す。Web は作成・会話・依頼への返事 (自動返信を含む)・日程調整・はじめての設定のテスト・下書きの承認で両方の一覧を付け、添付も全端末に包む。読む側 (会話、作成画面の返信の下準備、ブラウザの自動返信) は一覧から自分の端末の包みを選ぶ。受け取ったメッセージは、エージェントのどの端末の鍵でも試す
   - 手元で確かめたこと: ブラウザだけのエージェントから、ブラウザ + パソコン (core で作った 2 台目の端末) のエージェントへ送ると、パソコンは一覧の自分の包みで、ブラウザも一覧の自分の包みで開けた (相手の包みは開けない)。パソコンから送ったものは、送り手のブラウザが本人用の一覧で開けた (前からある 1 つだけの本人用の包みでは開けない)。手元の API は本文をファイルに置く方式で、ほかの利用者の本文を読めない (もとからの制限) ため、同じ利用者の 2 つのエージェントで確かめた
   - 残したもの: 古い受信箱の画面 (`/agent/<did>`、どこからもリンクしていない) と、パソコンの MCP (`runtime-gateway`) は段階 3 で
3. **パソコン側**: ゲートウェイと自動返信。v0.3.0 として配布
   - 実装 (2026-11-12): ゲートウェイの自動返信は、読むときに自分の DID の包み (DID がまだ分からないときは一覧の包みを順に) を先に試し、返事を相手と自分の全端末に包む (デーモンの `wrap_content_key` を端末の数だけ呼ぶ)。宛先の解決 (`resolve_recipient`) は `devices` をそのまま渡し、送信の中継は封筒の一覧をそのまま通す。クラウドの AI の `read_message` も、このパソコンの包みを先に使う。パソコンの MCP (`runtime-gateway`) も送るときに両方の一覧を付け、読むときは自分の包みを先に試す。署名デーモンは変えていない
   - 配布: v0.3.0 (2026-11-12、docs/32 §7.4)。動いているパソコンは、起動し直すと新しい版になる
   - 確かめたこと: `scripts/e2e_isolated_auto_reply.mjs` (実物のデーモン・ゲートウェイ・API) で、パソコンの自動返信が相手 1・自分 2 (パソコンとブラウザ) の端末に包まれ、ブラウザの鍵が自分の包みを開けることを確かめるようにした (PASS)。`scripts/e2e_remote_mcp_drafts.mjs` も PASS。ゲートウェイ 99 件、MCP 55 件のテスト
4. **画面**: 端末の一覧、新しい端末の知らせ。「パソコンをつなぐと、ブラウザでは読めなくなる」の説明を消す
5. **後で**: 端末の裏付け (§6 の 2) と、受け取る側での署名の確認。過去の分の引き継ぎ (§5.6)

各段で、手元で 2 人分 (ブラウザだけの相手、ブラウザ + パソコンの相手) の送り合いを確かめてから本番に出す。

## 9. 決めてほしいこと

- **Q1 方式**: A (送る側が全端末に包む) でよいか。推奨: A
- **Q2 段階 0**: 解除・緊急停止した端末の鍵を宛先から外す直しを、この設計とは別に先に出すか。推奨: 先に出す (小さく、安全に効く)
- **Q3 端末の上限**: 1 エージェントあたり 10 でよいか。推奨: 10
- **Q4 過去の分**: つなぐ前に届いたものを新しい端末でも読めるようにするか。推奨: 最初はしない (メッセージアプリと同じ)。要望が出たら §5.6 の形で足す
- **Q5 端末の裏付け**: 今回に含めるか、後にするか。推奨: 後。今回は「見えるようにする」(端末の一覧と新しい端末の知らせ) まで
