# 39. パソコン側の起動の手間を減らす (設計案、2026-11-12)

**Status**: B で進める (2026-11-12)
**運営者の判断 (2026-11-12)**: Q1 は B、Q2 は既定「いいえ」、Q3 は A の改善と B を**まとめて** v0.4.0 で出す、Q4 はインストーラを見送り
**Related**: [32 配布 §5](./32_daemon_distribution.md)、[37 使い始めの見直し §3](./37_first_run_review.md)、[31 オンボーディング](./31_onboarding_ux.md)、[38 複数端末](./38_multi_device_delivery.md)

## 1. 困っていること

- パソコンを再起動するたびに、ターミナルを開いて `nexusinbox start <フォルダ>` を打ち、パスフレーズを入れ直す必要がある。忘れると、自動返信もクラウドの AI も止まったまま。気づけるのはエージェント画面の「止まっています」だけ
- フォルダの場所を覚えていないと、起動のコマンドが分からない (画面は推測した場所を出している)
- 入れるのにターミナルと Homebrew が要る

## 2. いまの仕組み (2026-11-12 に確認)

- `nexusinbox connect <code>` が鍵を作り、`~/.nexusinbox/<名前>` に鍵ファイル (署名と暗号、Argon2id + XChaCha20-Poly1305 でパスフレーズから作った鍵で暗号化) と設定を置き、デーモンとゲートウェイを起動する
- `nexusinbox start <フォルダ>` は、ターミナルでパスフレーズを聞き、パイプで署名デーモンに渡す。デーモンは鍵を開けて、止まるまでメモリに持つ
- デーモンとゲートウェイは UNIX ソケット (0600) で話し、同じ利用者 (uid) のプロセスだけを受け付ける
- 配布物は Homebrew の tap。実行ファイルは ad-hoc 署名 (Apple の開発者証明書なし)。`/opt/homebrew` は利用者が書き込める
- docs/32 §2 の前提: 鍵はパソコンから出さない / 配る実行ファイルが本物だと確かめられる / 勝手に更新しない / 費用を増やさない

## 3. 何が変わると危ないか

鍵が狙われる場面を分けて考える。

| 攻撃者 | いま (手入力) | パスフレーズを保存して自動起動 |
|---|---|---|
| 同じ利用者として動くマルウェア (デーモン稼働中) | ソケット経由でデーモンに署名・鍵の開封を頼める (鍵そのものは取れない) | 同じ |
| 同じ利用者として動くマルウェア (鍵を持ち出したい) | 鍵ファイルは取れるが、パスフレーズが無いと開けない | **保存したパスフレーズを取れれば、鍵ごと持ち出せる** |
| パソコンを盗んだ人 (電源オフ) | ディスク暗号化 (FileVault) と鍵ファイルの暗号化の二重 | ログインのパスワードを知らなければ、キーチェーンは開かない |

つまり、変わるのは「稼働中に使われる」ではなく「鍵そのものを持ち出される」危険。持ち出されても、運営側は緊急停止 / 外す (docs/38 段階 0) で、その端末に新しいメッセージを包まなくできる。過去に届いた分 (送信から 90 日以内) は読まれうる。

## 4. 選択肢

| | やり方 | 良い点 | 気になる点 |
|---|---|---|---|
| A. いまのまま + 小さな改善 | 手入力は続ける。`nexusinbox start` をフォルダ指定なしで動かす (1 つしか無ければそれ)。止まっていたら「メッセージ」画面にも知らせる | 危険は増えない | 再起動のたびに打つのは変わらない |
| **B. キーチェーン + ログイン時に自動起動 (選んだ人だけ)** (推奨) | 「このパソコンにログインしたら自動で動かす」を選んだ人だけ、パスフレーズを macOS のログインキーチェーンに置く。読めるのは署名デーモンの実行ファイルだけ (キーチェーンの ACL)。launchd の LaunchAgent でログイン時に起動 | 再起動しても自動で戻る。パスフレーズはシェルや画面を通らない。オフにすれば元どおり | §3 の「持ち出し」の危険が増える (§5.3 の対策) |
| C. パスフレーズ無しの鍵ファイル | ファイルの権限 (0600) だけで守る | いちばん簡単 | 盗まれたディスクやバックアップから鍵がそのまま取れる。docs/31 で「空のパスフレーズでは暗号化しない」と決めている。却下 |
| D. 鍵そのものをキーチェーンに置く | 鍵ファイルをやめ、秘密鍵をキーチェーンの項目にする | ファイルが減る | B と危険は同じで、変更が大きい (鍵の保存形式、enroll、バックアップ)。B で足りる |
| E. ターミナル不要のインストーラ・メニューバーのアプリ | .pkg や常駐アプリにする | いちばん分かりやすい | ブラウザから配るには Apple の公証が要り、年 99 ドル (docs/32 §5)。「費用を増やさない」に反する。利用者が増えてから |

## 5. 推奨 B の中身

### 5.1 使い方

- `nexusinbox connect <code>` の最後に聞く: 「このパソコンにログインしたら、自動で動かしますか? (パスフレーズを macOS のキーチェーンに保存します) [y/N]」。既定は「いいえ」
- あとから切り替える: `nexusinbox autostart on <フォルダ>` / `nexusinbox autostart off <フォルダ>`。オンにするときはパスフレーズを 1 回入れ、鍵が開けることを確かめてから保存する
- フォルダを省略できるようにする (`~/.nexusinbox` に 1 つしか無ければそれ)。`start` / `stop` / `status` も同じ (A の改善も入れる)

### 5.2 しくみ

- 署名デーモンに `--passphrase-from-keychain` を足す (macOS だけ)。デーモン自身が Security フレームワークでキーチェーンを読む。パスフレーズはコマンドライン・環境変数・パイプを通らない
- キーチェーンの項目: ログインキーチェーンの汎用パスワード。サービス名 `ai.nexusinbox.signer`、アカウント名は資格情報の ID。ACL で読めるアプリを署名デーモンの実行ファイルだけにする
- 自動起動: `~/Library/LaunchAgents/ai.nexusinbox.<名前>.plist`。ログイン時に `nexusinbox run <フォルダ>` (前面で動き、デーモンとゲートウェイを子として持つ) を起動し、落ちたら launchd が起こし直す (`KeepAlive`、短時間に繰り返し落ちたら止まる)
- ログは `~/.nexusinbox/<名前>/run/` のまま
- `autostart off` は plist を消して launchd から外し、キーチェーンの項目も消す。緊急停止や「外す」をした端末は、API にトークンを断られて何もできない (自動で起こし直しても同じ)。そのパソコンでは `nexusinbox autostart off` で後片付けする

### 5.3 危険を増やしすぎないための決めごと

- **選んだ人だけ**: 既定はオフ。オンにするときに「鍵を持ち出される危険が少し増える」ことを一行で伝える
- **読めるのはデーモンだけ**: ACL で署名デーモンの実行ファイルに絞る。ad-hoc 署名なので、`brew upgrade` で実行ファイルが変わると、macOS が「キーチェーンを使ってよいか」を 1 回聞く (ログインのパスワードで「常に許可」)。これは仕様として受け入れ、`brew upgrade` のあとに出ることを案内する。別のプログラム (`security` コマンドを含む) が読もうとしても聞かれる
- **ログイン中だけ**: ログインキーチェーンは、ログアウト中・電源オフでは開かない
- **止める手段は今のまま**: 緊急停止・外す で、その端末に新しいメッセージを包まなくなる (docs/38)
- **画面で分かるように**: 「読める端末」の各パソコンに、自動起動がオンかを出すことはできない (サーバは知らない)。代わりに、止まっている時間が長いパソコンを「メッセージ」画面でも知らせる (A の改善)

### 5.4 Linux と Windows

- Linux: 今回はしない。手入力のまま。要望が出たら systemd のユーザーサービス + Secret Service (libsecret) で同じ形にする
- Windows: 配布自体がまだ (docs/32 §5)

## 6. 変えるところ

| 場所 | 変更 |
|---|---|
| 署名デーモン | `--passphrase-from-keychain <アカウント>` (macOS、`security-framework` クレート)。鍵が開けなければ終了 |
| `nexusinbox` (起動スクリプト) | `connect` の最後の問い、`autostart on/off`、`run` (前面で動く)、フォルダの省略 |
| Web | 止まっているパソコンを「メッセージ」画面でも知らせる。起動のコマンドを、フォルダを省略した形にする。help に自動起動の説明 |
| 配布 | 新しい版 (v0.4.0)。formula は変えない見込み |

マイグレーションと API の変更は要らない見込み。

## 7. 段階

1. **A の改善** (危険は増えない): フォルダの省略、止まっているパソコンを「メッセージ」画面で知らせる
2. **B**: キーチェーンと自動起動 (macOS)。手元で、ログアウト → ログイン、再起動、`brew upgrade` のあとの許可の問い、`autostart off` で元に戻ることを確かめる
3. v0.4.0 として配布

## 7.1 実装 (2026-11-12、手元)

- 署名デーモン: `--keychain-store <アカウント>` (パスフレーズを聞き、鍵ファイルが開けることを確かめてから保存)、`--passphrase-from-keychain <アカウント>`、`--keychain-delete <アカウント>`。macOS だけ (`security-framework`)。項目はデーモン自身が作るので、macOS は「作ったプログラム」を信頼し、ほかのプログラムには確認を出す。アカウントは資格情報の ID
- `nexusinbox`: `autostart on|off [<フォルダ>]`、`run [<フォルダ>]` (launchd 用。前面で両方を見張り、どちらかが止まったら両方止めて終了 → launchd が 30 秒あけて起こし直す)、`start` / `stop` / `status` のフォルダ省略 (`~/.nexusinbox` に 1 つだけのとき)。自動起動がオンのときの `start` は launchd に頼み、`stop` は launchd から外す (次のログインで戻る)。`connect` の最後に「ログインしたら自動で動かしますか? [y/N]」(macOS、ターミナルのときだけ)
- Web: 止まって 10 分以上たったパソコンを「メッセージ」画面でも知らせる (止まりごとに、このブラウザで閉じられる)。止まっているときの案内に `autostart on` を足した。help も
- 確かめたこと: キーチェーンへの保存 (違うパスフレーズは保存しない)、キーチェーンからの起動、削除。e2e (`e2e_isolated_auto_reply.mjs`) は新しいスクリプトで PASS
- まだ: launchd に実際に登録してログイン時に起動する流れ。運営者の Mac のログイン項目に足す操作なので、運営者の了承を得てから

## 8. 決めてほしいこと

- **Q1 方式**: B (選んだ人だけキーチェーン + 自動起動) でよいか。推奨: B
- **Q2 既定**: `connect` の問いの既定を「いいえ」にするか。推奨: 「いいえ」(危険が増えるので、選んだ人だけ)
- **Q3 順番**: A の改善を先に出し、B をそのあとにするか。推奨: A を先に (小さく、危険が増えない)
- **Q4 インストーラ (E)**: 今回は見送り、利用者が増えて Apple の費用を払う判断をしたときに考えるでよいか。推奨: 見送り
