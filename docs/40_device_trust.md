## 1. 困っていること

複数端末 (docs/38) で、送る側は相手のエージェントの全端末に本文の鍵を包むようになった。どの端末に包むかは、**運営のサーバが返す一覧をそのまま信じて**決めている。

そのため、運営 (またはサーバを乗っ取った人) は次のことができる。いまは「読める端末が増えました」の知らせで気づけるだけで、防げない。

1. **端末をこっそり足す**: ある AID に自分の鍵を足すと、それ以降そのエージェント宛てのメッセージが読める
2. **暗号の鍵を差し替える**: 本物の端末の DID はそのままで、暗号の鍵 (X25519) だけを自分のものに替える。DID (Ed25519) と暗号の鍵は、いまは何もつながっていない
3. **送り主を偽る**: 送り手の署名は送るときに API が確かめるだけで、保存も返却もしていない。受け取る側は確かめていないので、サーバは「アレックスさんから」と書いたメッセージを作って届けられる。自動返信がそれに反応する
4. **包みの一覧を書き換える**: 一覧 (`encrypted_keys`) は署名の外にある

「運営は鍵を持たない、運営にも読めない」を本当に言い切るには、1〜4 をサーバの善意に頼らず防ぐ必要がある。利用者がまだ運営者だけの今のうちに入れると、移行が楽になる。

## 2. いまの仕組み (2026-11-12 にコードで確認)

- **DID**: 端末ごとの `did:key` は Ed25519 の公開鍵そのもの。DID が分かれば署名の鍵は確かめられる (自己証明)。暗号の鍵 (X25519) は DID と別にサーバが返す
- **最初の端末**: エージェントを作ったブラウザ。`agents.did` がその DID で、署名の秘密鍵はそのブラウザの IndexedDB にある
- **パソコンをつなぐ**: ブラウザが接続コード (10 文字、50 ビット、サーバが作り、ハッシュだけを保存) を出し、パソコンで `nexusinbox connect <コード>` を打つ。パソコンは鍵を作り、所持証明を付けて有効にする。はじめての設定とエージェント画面は、有効になるまで 2 秒ごとに確かめている (ブラウザはその場にいる)
- **端末の一覧**: `GET /recipients/resolve` の `devices` と `GET /agents` の `devices`。どちらもサーバの言うとおり
- **署名**: 送り手は `sender_did / recipient_did / 件名の暗号文 / 本文の暗号文 / encrypted_key / nonce` に Ed25519 で署名する。API が送るときに確かめて捨てる
- **連絡先**: 名前とメモは端末で封をして `contacts.sealed` に置く (`cs1:`)。相手の DID を AAD に入れている。連絡先の鍵は利用者の全エージェントの鍵で包まれ、利用者のどの端末からも開ける
- **送る側の実装**: Web、core (パソコンの MCP、クラウドの AI 用の MCP)、ゲートウェイの自動返信 (Rust、署名はデーモン)

## 3. 守るもの・守らないもの

| | この設計で |
|---|---|
| 覚えている相手に、サーバが端末を足す・暗号の鍵を差し替える | **防ぐ**。送る側が包まない |
| サーバが送り主を偽る・封筒を書き換える | **防ぐ**。受け取る側が署名を確かめ、確かめられないものは印を付け、自動返信しない |
| 初めての相手 (まだ覚えていない) | 防げない (最初に見た鍵を信じる、TOFU)。あとで鍵が変われば気づける。見比べる手段は §9 |
| サーバが端末を隠す・メッセージを届けない | 防げない (届かないだけで、読まれはしない) |
| 端末そのものが乗っ取られる | 防げない。緊急停止と「外す」で、それ以降は包まない (今のまま) |
| メタデータ (誰から誰へ、いつ) | 対象外 (今のまま) |

## 4. 全体の形

### 4.1 ルート鍵

- エージェントごとに **ルート鍵** を 1 つ決める。エージェントを作ったブラウザの署名鍵 (= `agents.did`)
- ルート鍵が署名したものだけを、そのエージェントの端末として認める

### 4.2 端末の名簿 (署名つきの一覧)

ルート鍵は、端末の一覧全体に署名した **名簿** を出す。

```
{
  "v": 1,
  "aid": "aid:ai:...",
  "root": "did:key:z6Mk...(ルート)",
  "version": 7,                       // 増える一方
  "issued_at": "2026-11-12T10:00:00Z",
  "devices": [
    { "did": "did:key:...", "enc": "x25519 の公開鍵", "kind": "browser" },
    { "did": "did:key:...", "enc": "...", "kind": "computer" }
  ]
}
+ ルート鍵の署名
```

- 暗号の鍵は名簿の中で DID と結ばれる (§1 の 2 を防ぐ)
- 端末を足すとき・外すときに、ルートが新しい版を出す。`version` は増える一方
- サーバは名簿を保存して返すだけ (新しいテーブル `agent_device_lists`。中身は今も持っている DID と公開鍵だけ)。サーバには署名を作れない
- 名簿の端末ごとの名前 (パソコンの OS 名など) は入れない。表示はいまのままサーバの `devices` から取る (改ざんされても表示が変わるだけで、包む先は変わらない)

### 4.3 送る側が確かめること

1. 相手のルートを **覚える** (初めて見たときに保存。TOFU)
2. 名簿の署名をルートで確かめる。`version` が前に見たものより古ければ断る (古い名簿の使い回しを防ぐ)
3. **名簿にあり、かつサーバが今も有効と返す端末** にだけ包む
   - サーバが端末を外した (緊急停止・外す) ときは、ルートが新しい名簿を出す前でも、サーバの返事で外せる。サーバにできるのは「減らす」ことだけで、「足す」ことはできない
4. 相手のルートが覚えたものと違えば、送る前に止めて知らせる (§8)

### 4.4 受け取る側が確かめること (署名 v2)

- 送り手は、封筒全体 (宛先の AID、件名と本文の暗号文、2 つの包みの一覧、添付の包み、時刻) のハッシュに署名する。署名と送った端末の DID を、暗号文と一緒に保存先の JSON に入れ、`GET /messages/:id/content` で返す。DB の列は増やさない (送信から 90 日で消える)
- 受け取る側は、
  1. 送り手の名簿を取り、送り手のルートを覚えて (TOFU) 確かめる
  2. 送った端末がその名簿 (今の版か、前の版) にあることを確かめる
  3. 署名を確かめる
- 確かめられないメッセージには印を付ける。**自動返信 (パソコン・ブラウザ) は、確かめられたものにしか反応しない**
- 端末を外したあとも、その前に送られたメッセージを確かめられるように、サーバは名簿の古い版も残す (小さい。エージェントを消すときに一緒に消す)

### 4.5 覚えたルートの置き場

| 端末 | 置き場 |
|---|---|
| ブラウザ | 連絡先にいる相手は、連絡先の封 (`sealed`) の中。利用者の全端末で共有され、サーバには読めない。連絡先にいない相手は、そのブラウザの IndexedDB |
| パソコン (ゲートウェイ・MCP) | `~/.nexusinbox/<名前>/` の中のファイル |
| 自分のエージェント | ルートの鍵を持つブラウザは自分で分かる。パソコンは、つないだときに教わる (§5) |

## 5. 新しい端末を名簿に入れる (パソコンをつなぐとき)

名簿に足すにはルート (ブラウザ) が署名する。問題は、**ブラウザが「サーバが見せている鍵が、本当に自分がつないだパソコンの鍵か」を確かめる方法**。サーバが本物の代わりに自分の鍵を見せると、ブラウザはそれに署名してしまう。

| | やり方 | 良い点 | 気になる点 |
|---|---|---|---|
| **A. 接続コードに、サーバに送らない部分を足す** (推奨) | ブラウザが 80 ビットの秘密を作り、コードの後ろに足す (`XXXXX-XXXXX-XXXX-XXXX-XXXX-XXXX`)。前半はいまどおりサーバに、後半はブラウザとパソコンだけが知る。パソコンは自分の鍵にその秘密で MAC を付けて送り、ブラウザが確かめてから名簿に署名する。逆向きに、ブラウザはルートと名簿に MAC を付け、パソコンは自分のエージェントのルートを覚える | 利用者の手間は増えない (コマンドのコピーのまま)。つないでいる間にブラウザはその場にいるので、自動で署名できる。サーバは秘密を知らないので、鍵をすり替えられない | コードが長くなる (いまの 10 文字 → 26 文字)。パソコンとブラウザが別の機械で、手で打つ人にはつらい |
| B. 見比べる番号 | つないだあと、画面とターミナルに同じ 6 桁を出し、利用者が見比べて「同じ」を押す | コードは短いまま | 1 手増える。人はたいてい見比べずに押す。すり替えを防ぐにはコミットメントの手順も要り、作りが重い |
| C. 「わたしがつないだ」を押したら署名 | いまの「読める端末が増えました」の知らせのボタンで署名する | いちばん簡単。画面はほぼ今のまま | 利用者が本当につないだ直後にサーバがすり替えると、見分けがつかない。「別の時刻にこっそり足す」は防げる |

- A の秘密は 80 ビットにする。サーバは MAC と鍵を見られるので、短い秘密だと手元で総当たりされる (いまの 50 ビットでは足りない)
- A でも、ブラウザを閉じてしまったとき (コードの有効期限 10 分の間に戻ってこない) は、秘密を IndexedDB に残しておき、次にそのブラウザを開いたときに確かめて署名する。別のブラウザでは確かめられないので、C の形で聞く
- A は `nexusinbox connect` の引数の形が変わる。古いパソコン側 (v0.4.0 まで) は前半だけ受け付けるので、移行の間は C で認める

## 6. だれが名簿に署名できるか

- **推奨: ブラウザだけ**。最初はルートのブラウザ。ルートが認めたほかのブラウザも署名できる (将来、スマホや 2 台目のブラウザを足すとき)
- パソコン (デーモン) は署名しない。画面が無く、確かめる手段が無いため。パソコンが乗っ取られても、ほかの端末を足せない

## 7. ルートの鍵を失ったとき

ブラウザのデータを消すと、ルートの鍵 (と、そのブラウザの読む鍵) が消える。

- 名簿に署名できるほかのブラウザがあれば、それが続ける
- 無ければ、**新しいルートを作り直す**。相手から見ると「鍵が変わった」になる (§8)。メッセージアプリで端末を買い替えたときと同じ
- 鍵を書き出して保管する (バックアップ) は今回はしない。要望が出たら考える

## 8. 相手の鍵が変わったとき

- 相手のルートが、覚えたものと違うとき
- **推奨: 送る前に止めて知らせる** (「アレックスさんの鍵が変わりました。相手が端末を作り直したか、だれかがすり替えようとしています」。「確かめて送る」「やめる」)。受け取ったメッセージには印を付ける
- 自動返信は、鍵が変わった相手には反応しない (利用者が確かめるまで)
- 覚えたルートを更新するのは、利用者が「確かめて送る」を押したときだけ

## 9. 初めての相手を確かめる (後で)

- TOFU では、最初の 1 回にすり替えられると気づけない
- 後で、エージェント画面と連絡先に **確認番号** (自分と相手のルートから作る数字) を出し、別の手段 (会って、電話で) で見比べられるようにする。紹介ページ (`/to/<aid>`) はサーバが配るので、確認には使えない
- 今回は入れない

## 10. 移行

- 利用者は運営者だけ (2026-11-12)。いまのエージェントは、リリース後にルートのブラウザを開いたときに、今の端末の一覧をそのまま最初の名簿として署名する (一覧を見せて「この端末を認めます」)
- 名簿の無いエージェントには、これまでどおりサーバの一覧で包む (印を付ける)。署名の無いメッセージも、これまでどおり読めるが印を付ける。全員が新しい版になったら、名簿の無い相手には送らない形に切り替える
- 送る側の全部 (Web、core、ゲートウェイ、デーモン) が対応するので、パソコン側は新しい版 (v0.5.0) が要る

## 10.1 変えるところ

| 場所 | 変更 |
|---|---|
| API | 名簿の保存と返却 (`agent_device_lists`、マイグレーション 1 本)。署名の確認 (ルートの署名、`version` が増えていること、`aid` と `root` が合っていること)。`resolve` と `GET /agents` に名簿を足す。封筒の署名 v2 を受け取って保存・返却 |
| core | 名簿の確認、覚えたルートとの照合、名簿の端末にだけ包む、署名 v2 を作る・確かめる。テストベクタを Rust と共有 |
| Web | ルートとして名簿に署名 (作成時・パソコンをつないだとき・外したとき)。接続コードの後半 (A)。覚えたルートを連絡先の封と IndexedDB に。「鍵が変わりました」の確認。確かめられないメッセージの印。自動返信は確かめたものだけ |
| パソコン側 | ゲートウェイ: 名簿の確認、名簿の端末にだけ包む、署名 v2、受け取ったものを確かめてから自動返信。デーモン: 署名 v2 の入力を署名する。`connect` の新しいコード (A) と、自分のルートを覚える。v0.5.0 |
| 画面 | 「鍵が変わりました」、確かめられないメッセージの印、パソコンをつないだときの名簿への署名 (A なら表に出ない)。**画面は作る前に画面案を出す** |

## 10.2 段階

1. **名簿**: API (保存・確認・返却) と Web (ルートが署名、移行の最初の名簿)。送る側はまだ使わない (読むだけ)
2. **送る側が確かめる**: core と Web が名簿の端末にだけ包み、ルートを覚える。「鍵が変わりました」。パソコンをつなぐ流れ (§5 で選んだ方式)
3. **パソコン側**: ゲートウェイとデーモン。v0.5.0
4. **署名 v2 と受け取る側の確認**: 保存・返却、印、自動返信は確かめたものだけ
5. **締める**: 名簿の無い相手には送らない、署名の無いメッセージは自動返信しない (全員が新しい版になってから)
6. **後で**: 確認番号 (§9)、鍵のバックアップ (§7)

各段で、手元で 2 人分 (ブラウザだけの相手、ブラウザ + パソコンの相手) の送り合いと、「サーバが端末を足したとき」「暗号の鍵を差し替えたとき」「送り主を偽ったとき」を DB を直接書き換えて再現し、防げることを確かめる。

## 10.3 実装 (2026-11-12、段階 1)

- 画面案: `docs/40_device_list_mock.html`。運営者の判断「この案で、全て推奨どおり」(認めた端末には印を付けない、このブラウザからつないだ直後は自動で認める、はじめての案内を「メッセージ」にも 1 回出す)
- API: `PUT /agents/{id}/device-list` (人のセッションだけ)。署名は JWS (EdDSA、`typ: nexusinbox-device-list`、`kid` = ルートの DID)。ルート (`agents.did`) の有効な鍵で確かめ、`aid` と `root` が合い、端末が 1〜10 台で重複がなく、どれもそのエージェントの有効な端末でサーバの持つ暗号の鍵と同じで、版が保存済みより大きいときだけ保存する。版はすべて残す (マイグレーション 0032、`agent_device_lists`)。`GET /agents` と `GET /recipients/resolve` に最新の名簿 (`device_list: {version, jws}`)、`GET /agents` の各端末に `encryption_public_key`。監査ログに `device_list_signed`
- core: `@nexusinbox/core/device-list` (ブラウザでも使える。署名・確認・did:key から公開鍵)
- Web: `lib/agents/device-list.ts` (確認、このブラウザが見た最大の版を localStorage に覚えて古い名簿を見分ける、次の名簿を作る、署名して保存)
  - エージェント画面の「読める端末」: 名簿が無く端末が 2 台以上なら「この一覧を認めてください」。名簿にない端末に「まだ認めていません」と「認める」、鍵が違えば「認めたときと鍵が違います」。認められるのはルートの鍵を持つブラウザだけで、ほかのブラウザでは「エージェントを作ったブラウザで認めてください」。「外す」のあとは、外した端末を除いて署名し直す。名簿がおかしいとき (署名が合わない・前に見た版より古い) は警告を出し、今の端末を認め直せる (版は、このブラウザが見た最大の版より上にする)
  - 「メッセージ」: 端末がこのブラウザだけなら黙って認める。2 台以上で名簿が無ければ 1 回だけ「読める端末を確かめてください」。名簿がおかしい・鍵が違うときは「端末の一覧が、あなたが認めたものと違います」と緊急停止。「読める端末が増えました」の「わたしがつないだ」は、ルートのブラウザでは「わたしがつないだ（認める）」になり、増えた端末を足して署名する
  - このブラウザでパソコンをつないだ直後 (はじめての設定・エージェント画面) は、その資格情報の端末だけを足して署名する (§5 の C。A は段階 2)
- 確かめたこと: API の DB テスト (ルート以外の署名、暗号の鍵の差し替え、ほかのエージェントの端末、署名後の書き換え、ほかのエージェント名、古い版、ほかの人の保存を断る)、core と Web の単体テスト。手元のブラウザで、エージェントを作る → 「メッセージ」で黙って版 1 → パソコン役を DB に足すと「まだ認めていません」→「認める」で版 2 → DB で暗号の鍵を差し替えると「メッセージ」に警告 → 版 2 を消すと「古い名簿」の警告 → 認め直して版 3 → 「外す」で版 4 (パソコン抜き) → 2 台目を足して「わたしがつないだ（認める）」で版 5
- 送る側はまだ名簿を使わない (段階 2)

## 11. 決めてほしいこと

- **Q1 形**: 端末ごとの証明書ではなく、一覧全体に署名する名簿 (`version` つき) でよいか。推奨: 名簿 (外したことも表せて、古い一覧の使い回しを `version` で防げる)
- **Q2 パソコンを認める方法 (§5)**: A (コードに秘密を足す、26 文字) / B (見比べる番号) / C (「わたしがつないだ」で署名)。推奨: A。移行の間と、別のブラウザで見たときは C
- **Q3 署名できる端末 (§6)**: ブラウザだけでよいか。推奨: ブラウザだけ
- **Q4 鍵が変わったとき (§8)**: 送る前に止めて確かめるか、知らせるだけか。推奨: 送る前に止める
- **Q5 確かめられないメッセージ (§4.4)**: 印を付けて読めるようにし、自動返信はしない、でよいか。推奨: それで
- **Q6 確認番号 (§9)**: 今回は入れず後にするか。推奨: 後

## 12. 段階 2 の設計 (案、2026-11-13)

段階 2 では、送る側が相手の名簿を確かめ、名簿にある端末にだけ鍵を包む。相手のルートを覚え、変わったら送る前に止める (§4.3、§8)。

### 12.1 範囲 (§10.2 からの組み替えの提案)

- **段階 2 はブラウザだけにする。** 確かめる規則は core に置き (`@nexusinbox/core/device-list` に足す)、段階 3 でパソコン側も同じ規則を使う。Rust のゲートウェイと共有するテストベクタも作る
- **接続コード A (§5) は段階 3 に回す。** いまのパソコン側 (v0.4.0) は、コードをそのまま API に送る。API は 10 文字でなければ断る。そのため、Web だけ先に長いコードを出すと、いまのパソコンがつなげなくなる。A は新しい `connect` (v0.5.0) と一緒に入れる。段階 2 の間は、段階 1 の「このブラウザでつないだ直後に自動で認める」(C) のまま
- **パソコン側で送るものは段階 3 にする。** ゲートウェイの自動返信 (Rust) と、TS の MCP 2 種 (`runtime-gateway`、`runtime-saas`) が該当する。それまでは今までどおり、サーバの一覧で包む
- **API は変えない。** `resolve` が名簿を返すところまでは、段階 1 で済んでいる

### 12.2 ブラウザで送る場所

鍵を包む処理は、どれも `lib/crypto/device-wraps.ts` (`deviceWraps` / `agentDevices` / `wrapContentKeyForDevices`) を通っている。ここを「確かめてから包む先を返す」1 つの関数に置き換えれば、次の場所すべてに効く。

| 送る場所 | ファイル |
|---|---|
| 新しい会話 (添付の包みも) | `app/compose/page.tsx` |
| 会話での返信 | `_components/messages/ConversationView.tsx` |
| 予定の提案・返事 | `lib/protocol/send-propose.ts`、`_components/protocol/sendProtocolReply.ts` |
| ブラウザの自動返信 | `_components/BrowserAutoReply.tsx` (→ `sendProtocolReply`) |
| クラウドの AI の下書きを承認して送る | `lib/crypto/review-key.ts` |

1 つだけの包み (`encrypted_key`。古い読み手のための包み) の宛先も、いまはサーバが選んでいる (`resolve` の `did` と `encryption_public_key`)。これも §12.3 の 6 で、名簿から選び直す。

### 12.3 包む先の決め方

`resolve` の返事 (`aid`、`did`、`devices`、`device_list`)、覚えたルート (§12.4)、問い合わせた宛先 (AID か DID) から、次の順に決める。

1. **名簿が無い**
   - 前にこの相手の名簿を見たことがある → 止める (名簿を消された)
   - 見たことがない → 今までどおり、サーバの一覧で包む (名簿の無い相手として扱う。段階 5 まで)
2. **名簿を確かめる**
   - 名簿の署名を、名簿に書かれたルートの鍵で確かめる (`did:key` なので、DID から鍵が分かる)
   - 名簿の `aid` が、`resolve` の `aid` と同じであること。AID で問い合わせたときは、その AID とも同じであること
   - DID で問い合わせたときは、その DID が前に見たのと同じエージェントのものであること。サーバが DID を別のエージェントに結び付けるのを防ぐ。どのエージェントの DID かは、このブラウザと連絡先の封が覚えている
     - 当初は「その DID が名簿にあること」としていた。だが会話はパソコンの DID で続くことがあり、パソコンを外すとその会話から送れなくなる。また、偽の名簿はどの DID でも書き込めるので、守りとしても弱い。そのため確認中 (2026-11-13) にこの形に改めた
   - どれかが合わなければ止める
3. **ルートを比べる**
   - 覚えていない → 覚える (TOFU)
   - 覚えたものと違う → 「鍵が変わりました」(§12.5)
4. **版を比べる**: 覚えた版より古ければ止める (古い名簿に戻された)
5. **包む先**
   - 名簿の端末のうち、サーバが今も返す端末だけに包む (DID で突き合わせる)。暗号の鍵は、名簿に書かれた鍵を使う
   - サーバにできるのは減らすことだけで、足すこと・差し替えることはできない
   - 包む先が 0 台なら止める
6. **1 つだけの包み**
   - サーバが返した `did` が包む先にあれば、その端末に包む
   - 無ければルートの端末、ルートも包む先に無ければ包む先の最初の端末に包む
7. 覚えた版を、この名簿の版に上げる

**自分の写し** (`sender_encrypted_keys`) にも、同じ規則を自分のエージェントに当てる。

- ルートの鍵を持つブラウザは、自分のルートを確かに知っている
- 自分の名簿がおかしいときも、送ることは止めない。写しは端末ごとには包まず、1 つだけの写し (`sender_encrypted_key`) だけにする (エージェント画面と「メッセージ」には、段階 1 の警告が出ている)
  - その 1 つの写しの鍵は、今のところサーバが返すものを使う。ブラウザが自分の暗号の公開鍵を覚えるようにすれば、これも確かめられる (後で)

| 状況 | 人が送る | 自動返信・下書きの自動処理 |
|---|---|---|
| 名簿があり、合っている | 名簿 ∩ サーバの有効な端末に包む | 同じ |
| 名簿が無く、見たこともない | サーバの一覧で包む。宛先の下に「端末の名簿がまだありません」(Q8) | 今までどおり送る (段階 5 で止める) |
| 名簿が無いが、前に見た | 止める | 送らない |
| 署名が合わない・`aid` が違う・DID が名簿に無い | 止める | 送らない |
| 版が古い | 止める | 送らない |
| ルートが変わった | 「鍵が変わりました」(§12.5) | 送らない |
| 包む先が 0 台 | 止める | 送らない |

「止める」は、送る前に理由を出し、送らないことを指す。下書きは消さない。

### 12.4 覚えたルートの置き場

- **このブラウザ (localStorage)**: 「相手のルート」の置き場。`aid` ごとに `{ root, version }` を持つ。DID ごとに、どのエージェントのものかも覚える
  - 段階 1 で置いた「このブラウザが見た最大の版」も、ここへ移す。自分のエージェントと相手を同じ置き場で扱う
  - 案では IndexedDB にするつもりだった。段階 1 と同じ localStorage にしたのは、送る前の同期の確認で読めるようにするため。どちらも同じオリジンの中で、守りの強さは変わらない
- **連絡先の封**: 連絡先にいる相手は、封 (`cs1:`) の中にも `aid` と `root` を入れる。形式名は `cs1` のまま、欄を足す
  - 封の中と IndexedDB で覚えたルートが違えば、「鍵が変わりました」として扱う
  - 封の中に書くのは、連絡先を保存するときと、鍵を覚え直したとき
  - これで、利用者の別のブラウザでも、連絡先の相手のルートがそろう (§4.5)

### 12.5 「鍵が変わりました」

- ルートは `agents.did` で、いまは正当に変わる道が無い (§7 の作り直しは後で入れる)。そのため、いま変わったなら、サーバが別のものを見せている可能性が高い。文言はその前提で書く
- **人が送るとき**: 送る前に止める
  - ボタンは「やめる」(主) と「確かめたので送る」の 2 つ
  - 「確かめたので送る」はもう一度確認したうえで、新しいルートを覚え直して送る (§8)
- **自動返信・下書きの自動処理**: 送らない
- 受け取ったメッセージに印を付けるのは段階 4 (署名 v2)。段階 2 では、送るときにだけ確かめる

### 12.6 画面 (作る前に画面案を出す)

- 送る前に止める画面: 「鍵が変わりました」、「端末の名簿がおかしい / 古い名簿に戻された」、「読める端末がありません」の 3 種
- 名簿の無い相手へ送るときの小さな一行 (Q8)
- それ以外の画面は変えない (名簿が合っている相手には何も出さない)

### 12.7 確かめ方

- core の単体テストと、テストベクタ `tests/vectors/device_list_decisions.json` (§12.3 の表の全行。段階 3 で Rust も同じものを通す)。Web の単体テスト
- 手元のブラウザで、同じ利用者の 2 つのエージェントを使う (A はブラウザだけ、B はブラウザとパソコン役)
  - B に名簿に無い端末を DB で足す → A から B に送った封筒の `encrypted_keys` に、その DID が無い
  - B の端末の暗号の鍵を DB で差し替える → 包みは名簿に書かれた鍵で作られ、B のブラウザで読める
  - B の名簿を消す → 送る前に止まる
  - B の `agents.did` と名簿を、別の鍵のものに替える → 「鍵が変わりました」。自動返信は送らない
  - 上のそれぞれを、新しい会話・返信・予定の返事・下書きの承認で確かめる

### 12.8 決めてほしいこと

- **Q7 範囲の組み替え (§12.1)**: 段階 2 はブラウザだけにし、接続コード A とパソコン側で送るものは段階 3 (v0.5.0) に回す。推奨: そうする (いまのパソコンが、長いコードでつなげなくなるため)
- **Q8 名簿の無い相手 (§12.3)**: 今までどおりサーバの一覧で送り、宛先の下に「端末の名簿がまだありません」と小さく出す (止めない)。推奨: それで (止めるのは、全員が新しい版になってからの段階 5)

## 13. 段階 3 の設計 (案、2026-11-13)

段階 3 では、パソコン側でも送る前に相手の名簿を確かめる (§12 と同じ規則)。あわせて、接続コードに秘密を足し (§5 の A)、ブラウザが「サーバが見せている鍵が、本当に自分がつないだパソコンの鍵か」を確かめてから名簿に署名する。パソコン側は v0.5.0 として出す。前回外したローカルの窓口 (docs/22) の削除も、このリリースで一緒に出る。

### 13.1 パソコン側で送る場所 (2026-11-13 にコードで確認)

| 送る場所 | 鍵を包むのはだれか | いま包む先を決めているもの |
|---|---|---|
| ゲートウェイの自動返信 | ゲートウェイ (包むのはデーモン) | `auto_reply_executor.rs` の `seal_reply` (`resolve` の `devices` をそのまま使う) |
| パソコンの AI ツール (TS の MCP、`runtime-gateway`) | TS の MCP。署名はゲートウェイ経由でデーモン | `runtime-gateway.ts` がゲートウェイの `resolve_recipient` を呼び、その `devices` を使う。ゲートウェイの `send_message` は、宛先をもう一度 `resolve` して署名する |
| クラウドの AI の下書き | ゲートウェイ (`remote_mcp.rs` の `create_draft`) | `resolve` の `did` と `encryption_public_key` に 1 つだけ包む。端末ごとの包みは、ブラウザで承認するときに足す (段階 2) |
| SaaS モードの MCP (`runtime-saas`、ゲートウェイなし) | TS の MCP | `client.resolveRecipient` の `devices` |

自分の写しは、どれもデーモン自身の鍵で包んでいる。この鍵はパソコンが確かに知っているので、確かめなくてよい。

### 13.2 確かめる場所: ゲートウェイに 1 つ

- **ゲートウェイが判定し、覚えたルートもゲートウェイだけが持つ。** 規則は core の `decideWrapTargets` を Rust に移したもので、共有テストベクタ `tests/vectors/device_list_decisions.json` を両方で通す
- ゲートウェイの `resolve_recipient` (RPC) は、確かめた結果を返す
  - 合っている: 包む先の端末 (名簿の鍵) と、1 つだけの包みの宛先
  - 止める: 理由つきのエラー
  - TS の MCP (`runtime-gateway`) は、返ってきた端末だけに包む。判定は自分でしない
- ゲートウェイの `send_message` (RPC) は、署名する前にもう一度判定する。次の場合は断る
  - 封筒の宛先 (`recipient_did`) が、判定した 1 つだけの包みの宛先と違う
  - `encrypted_keys` に、包む先以外の DID がある
  - こうして、MCP 側の書き違いもここで止まる
- 自動返信 (`seal_reply`) と下書き (`create_draft`) も、同じ判定を通す。下書きは、1 つだけの包みを判定した宛先に作る
- `runtime-saas` は、core の `decideWrapTargets` をそのまま使う。覚えたルートは、鍵の置き場と同じフォルダのファイルに置く

**覚えたルートの置き場**: エージェントのフォルダ (`~/.nexusinbox/<名前>/`) の `peers.json` (0600、書き換えは一時ファイルから置き換え)。`aid` ごとの `{root, version}` と、DID ごとのエージェントを持つ。

### 13.3 止めたとき

| 送る場所 | 止めたとき |
|---|---|
| 自動返信 | 送らない。返信の受け持ちは解かず、人に任せる (ブラウザと同じ) |
| パソコンの AI ツール | ツールのエラーで理由を返す。AI はそれを人に伝える |
| クラウドの AI の下書き | 下書きを作らず、ツールのエラーで理由を返す |

- **自動返信を見送ったことを、サーバに記録する (Q10)。** パソコンが見送っても、ブラウザでは気づけないため
  - API を 1 つ足す: `POST /messages/:id/auto-reply-skip`。中身は理由のコードだけ
  - サーバは監査ログに `auto_reply_skipped` を残す。「AI の操作履歴」と、その会話に「自動返信しませんでした」が出る
  - ブラウザの自動返信も同じ API を使う。段階 2 で localStorage に置いた記録は、これに置き換える
- **鍵が変わった相手を、パソコンで受け入れる (Q9)。** コマンド `nexusinbox trust <宛先>` を足す
  - 新しいルートの DID を見せ、`y` で覚え直す
  - いまは正当にルートが変わる道が無いので、めったに使わない
  - ブラウザで「確かめたので送る」を押しても、パソコンの覚えは変わらない (別々に覚えている)

### 13.4 自分のエージェントのルート

- パソコンは、自分のエージェントのルートも覚える。自分の写しを、ほかの端末 (ブラウザなど) に包むときに使う
- 接続コード A でつないだパソコンは、つなぐときにルートを確かに教わる (§13.5)
- それより前につないだパソコンは、v0.5.0 で最初に起動したときに、そのとき見えた名簿のルートを覚える (TOFU)

### 13.5 接続コードに秘密を足す (§5 の A)

**コードの形**: いまの 10 文字の後ろに、ブラウザが作った 16 文字 (80 ビット) を足す。

```
nexusinbox connect 7KQ4P-ZX9M2-H3TD-9QWB-0KMA-R4XE
                   └ サーバに渡す ┘ └ ブラウザとパソコンだけ ┘
```

**流れ**

1. ブラウザ (エージェントを作ったブラウザ) が秘密を作る
   - 秘密は IndexedDB に資格情報 ID ごとに覚え、コマンドに足して見せる
   - サーバには前半の 10 文字だけが渡る (いまと同じ)
2. パソコンの `connect` は、コードを前半と後半に分ける
   - 前半で、いまどおり問い合わせて有効にする
   - そのとき、自分の DID と暗号の鍵に、秘密で作った MAC を付けて送る
   - 秘密は、ルートを確かめるまでエージェントのフォルダに置く (0600)
3. ブラウザは、パソコンが有効になったのを見たら次を行う (いまも 2 秒ごとに見ている)
   1. サーバが返すそのパソコンの DID と暗号の鍵で、MAC を確かめる
   2. 合えば名簿に足して署名する
   3. ルートと AID にも秘密で MAC を付けて、サーバに置く
4. パソコン (ゲートウェイ) は、起動したときにルートの MAC を受け取って確かめ、自分のエージェントのルートとして覚える。そのあと秘密を消す

**MAC の形**

```
HMAC-SHA256(秘密, "nexusinbox-pair-device-v1\n" + 資格情報ID + "\n" + DID + "\n" + 暗号の鍵)
HMAC-SHA256(秘密, "nexusinbox-pair-root-v1\n"   + 資格情報ID + "\n" + AID + "\n" + ルート)
```

- TS と Rust で同じテストベクタ (`tests/vectors/pairing_mac.json`) を通す
- サーバは MAC と、その元の値を見られる。それでも秘密は 80 ビットあるので、手元で総当たりはできない

**うまくいかないとき**

| 状況 | 動き |
|---|---|
| MAC が合わない (サーバが鍵をすり替えた) | 自動では認めない。エージェント画面と「メッセージ」に「つないだパソコンの鍵と、サーバが見せる鍵が違います」を出し、「外す」と緊急停止を出す |
| ブラウザを閉じた (10 分の間に戻らなかった) | 秘密は IndexedDB に残る。次にそのブラウザで「メッセージ」かエージェント画面を開いたときに、確かめて署名する |
| 別のブラウザで接続コードを出した | そのブラウザはルートの鍵を持たないので、いまどおり C (エージェントを作ったブラウザで「認める」) |
| 古いパソコン側 (v0.4.0 まで) に長いコードを打った | 古い `connect` は 10 文字以外を手元で断るので、秘密はどこにも送られない。Web のコマンドの横に「v0.5.0 以上が要ります (brew upgrade nexusinbox)」と出す |

### 13.6 変えるところ

| 場所 | 変更 |
|---|---|
| API | マイグレーション 1 本: `agent_credentials` に `pairing_device_mac` と `pairing_root_mac` を足す (どちらも MAC だけで、秘密は持たない。資格情報を消すと一緒に消える)。有効にするときに MAC を受け取る。`GET /agents` の端末に MAC を足す。ブラウザがルートの MAC を置く `PUT`、パソコンが読む `GET` (自分の資格情報だけ)。`POST /messages/:id/auto-reply-skip` (Q10) |
| デーモン | `connect`: コードを分ける、端末の MAC を送る、秘密を置く。ローカルの窓口の削除 (docs/22、コードは済み) |
| ゲートウェイ | 判定の Rust 版 (共有ベクタ)。`peers.json`。`resolve_recipient` / `send_message` / 自動返信 / 下書きで判定する。起動時に自分のルートを確かめて覚える。見送った自動返信をサーバに知らせる |
| スクリプト | `nexusinbox connect` は長いコードをそのまま渡す。`nexusinbox trust` を足す |
| TS の MCP | `runtime-gateway`: ゲートウェイが返す包む先を使う。`runtime-saas`: core の判定とファイルの置き場 |
| Web | 接続コードの秘密 (作る・覚える・確かめる・ルートの MAC を置く)。MAC が合わないときの知らせ。下書きの承認で、下書きの宛先が包む先に入っていることも確かめる。自動返信の見送りをサーバに知らせ、会話の一行はサーバの記録から出す |
| 画面 | 長いコードと「v0.5.0 以上が要ります」。MAC が合わないときの知らせ。「AI の操作履歴」の「自動返信しませんでした」。**作る前に画面案を出す** |

### 13.7 出す順番

1. API (MAC と見送りの記録を、受け付けるだけ) と Web の確かめる側を出す。この時点では長いコードはまだ出さない
2. パソコン側 v0.5.0 をリリースし、Homebrew の formula を更新する
3. Web が長いコードを出すようにする

利用者は運営者だけなので、2 と 3 の間に古いパソコン側が残っても、Web の案内で上げてもらえば足りる。

### 13.8 確かめ方

- 共有ベクタ (判定 17 件、MAC) を TS と Rust で通す
- 手元で、パソコン役のデーモンとゲートウェイを動かして試す (`scripts/run_noninteractive_stack.sh`)
  - 長いコードでつなぐ → ブラウザが MAC を確かめて自動で認め、パソコンが自分のルートを覚える
  - DB でパソコンの暗号の鍵をすり替えてからつなぐ → 自動では認めず、知らせが出る
  - 相手の名簿をすり替える (§12.9 と同じ 4 通り) → 自動返信は送らず、「AI の操作履歴」に出る。MCP の送信と下書きはエラーになる
  - `nexusinbox trust` で覚え直す → 送れる

### 13.9 この段階でも守らないもの

- **下書きを読めるブラウザの一覧** (`/review-keys`) は、いまもサーバの言うとおり。サーバがここに自分の鍵を足すと、クラウドの AI の下書きが読める。名簿と同じくルートが署名する形にできるが、段階 3 には入れない (後で)
- 送り主の確認 (受け取る側で署名を確かめる) は段階 4

### 13.10 決めてほしいこと

- **Q9 鍵が変わった相手を、パソコンで受け入れる方法 (§13.3)**: `nexusinbox trust <宛先>` コマンドを足す / パソコンでは受け入れず止めたままにする。推奨: コマンドを足す
- **Q10 自動返信の見送りをサーバに記録するか (§13.3)**: 記録する (監査ログに理由のコードだけ。「AI の操作履歴」と会話に出る) / パソコンのログだけにする。推奨: 記録する (パソコンが黙って見送ると、人が気づけない)
- **Q11 出す順番 (§13.7)**: API と Web の確かめる側 → v0.5.0 → 長いコード。推奨: この順
- **Q12 下書きを読めるブラウザの一覧 (§13.9)**: 段階 3 には入れず後にする。推奨: 後
