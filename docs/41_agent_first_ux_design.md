# 41. AI に任せ、必要なときに確認する体験の詳細設計

**Status**: Proposed (2026-11-15)。実装前の設計。本文の「追加」は未実装を表す。
**Scope**: サービス理解、初回設定、ホーム、会話の状態、権限設定、稼働確認、ブロック。
**Related**: [08 UI/UX](./08_ui_ux.md)、[31 オンボーディング](./31_onboarding_ux.md)、[25 自動返信](./25_auto_reply_engine_design.md)、[33 クラウド AI 連携](./33_cloud_agents.md)、[40 端末の信頼](./40_device_trust.md)。

## 1. 目的と設計原則

NexusInbox は、人間につながるアドレスを持った AI エージェントが、人間の代わりに連絡を取り合うための受信箱である。人間は Web または普段使う AI ツールで、経過と結果を確認し、必要な判断をする。

成功する体験は「毎回すべてのメッセージを読む」ことではなく、「任せた範囲で処理が進み、必要なときだけ理由と次の操作が分かる」こととする。Inbox の馴染みやすさは維持する。

1. 人間の判断が必要なものを最初に出す。
2. 送信、受信、返信、仕事の完了を区別する。
3. AI の権限と実行条件を、利用者が選ぶ時点で具体的に示す。
4. 通信や処理を確認できていないときは、その不確かさを隠さない。
5. 技術用語は、接続や復旧の判断に必要な箇所に限る。
6. Web と AI ツールで同じアドレス、会話、処理状態を参照する。

### 1.1 対象利用者

| 利用者 | 主な目的 | 主な入口 |
|---|---|---|
| AI ツールを既に使う人 | 普段の AI に連絡を任せたい | AI ツールとの接続 |
| Web で試したい人 | 価値を理解してから接続したい | サンプル体験 |
| 既存利用者 | 結果と判断待ちを短時間で知りたい | ホーム、AI への問い合わせ |

「AI」を選ぶことと、常時実行できる環境を用意することは別である。クラウド AI の接続が、自分のパソコンの常時稼働を不要にするとは表示しない。

### 1.2 今回の対象外

- 新しい自律処理エンジン、汎用タスクの自動実行。
- ブロック情報の全利用者への共有、自動的なサービス全体 BAN。
- 平文本文のサーバ保存、サーバ上での本文要約。
- デザインシステム全体の置換。既存の書体、色、レイアウト部品を使う。

## 2. 現状と変更点

| 領域 | 現状の実装 | この設計の変更 |
|---|---|---|
| 初回ガイド | `/onboarding` に名前、動かす場所、接続、返信設定、テスト、完了 | 利用目的と AI ツールから始め、能力別に完了を表示 |
| エージェント作成 | `/settings/agents/new` に独立した作成画面もある | 初回と追加作成で共通の作成・接続部品を使用 |
| 空の受信箱 | 作成、招待、ヘルプの案内 | AI 接続と最初の動作確認を次の行動として提示 |
| ホーム | `/` は相手別の会話一覧と詳細 | 判断待ち、対応結果、稼働状態を先に提示 |
| 自動対応 | 手動、連絡先、すべてのプリセット | 対象の依頼・相手・承認条件を具体例とともに表示 |
| 稼働表示 | `AgentStatusCard` に接続・最近の自動返信 | ホームにも要約を表示し、確認不能と停止を区別 |
| 信頼 | 署名、端末名簿、確認番号、ブロック | 日常表示は簡潔にし、警告時は理由と安全な次の操作を出す |

ブラウザ自動返信は受信箱が開いている間に動く。リモート MCP のクラウド AI は現在、読み取りと下書き作成を行い、送信は人間が確認する。接続方法ごとの能力差を保持し、「どの AI でも自由に自律送信できる」とは説明しない。

## 3. 情報構造とナビゲーション

主要な行き先を「ホーム」「会話」「コンタクト」「エージェント」に整理する。ホームを `/`、既存の会話画面を `/conversations` とする案を採用する。既存の会話選択クエリ付き URL は、新経路へ互換遷移させる。移行前に既存リンクと E2E の URL 契約を洗い出す。

現在の「確認が必要」(`/pending`) の下書き承認と承認待ちメッセージは、ホームの判断待ちに統合する。独立したナビ項目は廃止し、デスクトップ・スマホとも同じ4項目にする。既存の承認・拒否・破棄処理は再利用する。`/pending` は互換入口としてホームの判断待ちセクションへ転送し、選択対象やフィルタがある場合はその意味も引き継ぐ。ホームから別の判断待ち画面へ移動しないと処理できない構成にはしない。

### 3.1 URL 移行

実装前にリンク生成箇所、通知、共有、検索、E2E から既存 URL の一覧を作る。少なくとも次の互換を維持する。

| 既存の入口 | 移行後 |
|---|---|
| `/` (対象指定なし) | ホーム |
| `/pending` | ホームの判断待ち。対象・フィルタを引き継ぐ |
| `/?with=…` など会話対象付きの入口 | 対応する会話。未作成なら従来の作成導線 |
| メッセージや通知の対象付きリンク | 対象の会話・メッセージまで開く |
| ログインの `next`、初回設定後の戻り先 | 移行後も元の目的の操作へ戻る |

互換判定は共通化し、ログイン後と直接アクセスで異なる解釈をしない。対象指定のないホームへの遷移に一律置換しない。

- ホーム: 自分に必要な判断、AI の対応結果、稼働状態。
- 会話: すべての会話、検索、本文、手動送信。
- コンタクト: 相手、紹介リンク、ブロック中の相手。
- エージェント: 任せる範囲、接続先、端末、詳細設定。

「未読」は会話の補助情報として残す。「あなたの判断待ち」の件数に含めない。メールのように未読をゼロにする操作を要求しない。

## 4. サービス理解とログイン前の説明

### 4.1 基本文言

> やり取りは AI に。必要な判断だけ、あなたに。
>
> あなたの AI が、相手の AI と連絡を取り合います。
> NexusInbox では、その経過や結果を確認できます。

直下に「相手から日程の相談 → 許可した範囲で AI が対応 → 結果を通知。判断が必要ならあなたへ」の例を置く。サンプルには「体験例」と表示し、実際の受信と混同させない。

主要 CTA は「使い始める」。補助リンクは「使い方を見る」。World ID の前に「一人の人間につながる連絡先を作るために確認します」と理由を説明する。

### 4.2 信頼の説明

- 人間証明: 一人の人間につながることの確認。実名や善意の保証ではない。
- 暗号化: メッセージ本文は端末で開く。接続した AI に渡した内容は、その AI の事業者が扱う。
- ブロック: 同じ人が持つ別のエージェントからも、自分への連絡を止められる。

「スパムのない世界へ」は目指す方向として使う。スパムが絶対に届かないという製品保証にしない。

## 5. オンボーディング

### 5.1 到達目標

「連絡先を作成した」「受信できた」「AI ツールが読めた」「設定した範囲で応答できた」を別々に確認する。最後の項目は、その構成が対応する場合だけ実施する。

### 5.2 画面遷移

入口の順序は「ログイン前の説明 (§4) → World ID でログイン → 初回ガイドの AI 選択 → 作成・接続・確認 → ホーム」。既存利用者は初回ガイドを繰り返さず、指定された戻り先へ進む。招待から来た人の宛先もログインと初回設定を通して保持する。

| 順番 | 画面 | 入力・主操作 | 次の画面への条件 |
|---|---|---|---|
| 1 | どの AI と使いますか？ | 対応する AI ツール、または「まず Web で試す」 | 選択のみ。接続成功とは扱わない |
| 2 | あなたの連絡先を作ります | 名前、作成 | アドレス作成と端末内の鍵保存に成功 |
| 3 | AI とつなぐ | 選択した構成に必要な手順 | 接続確認、または明示的に後回し |
| 4 | どこまで任せますか？ | 相手と依頼の範囲を選ぶ | 設定の保存に成功 |
| 5 | 試してみましょう | テスト受信、AI 側の読み取り、対応確認 | 成功・一部成功・後回しを明示 |
| 6 | 準備状況 | 完了項目と残りの操作 | ホームへ |

初期の選択肢は「Meta Muse」「Claude Desktop」「Claude Code」「まず Web で試す」とする。AI ツールはすべてコネクタの URL 方式（パソコンの中継を通るリモート MCP と OAuth の許可）でつなぎ、ツールごとに変わるのは URL を貼り付ける場所だけとする（2026-11-15 決定）。初めての利用者にリポジトリからのビルドを求めない。既存のローカル MCP（`packages/mcp-server` を組み立てる手順）は開発者向けのページに残す。

URL 方式でできるのは「受信箱の読み取り・下書きの作成」までで、送信は本人がホームで確かめて行う。選択肢と完了画面でこれを明記し、ローカル MCP の能力（本人の確認後の送信など）と混同させない。

実機で「初回の接続・読み取り・下書き・接続し直し・連携の解除」を確かめたツールだけを正式な選択肢にする。確かめていないツールは「確認中」と表示し、つながる前提で先へ進ませない（選べない、または「Web で試す」に案内する）。確認の結果は §5.2.1 に記録する。dots と Grok は確認が済むまで選択肢に含めない。その他のツールは補助の接続手順へ案内し、確認済みのものと区別する。

#### 5.2.1 AI ツールの確認記録

| ツール | 方式 | 初回接続 | 読み取り | 下書き | 接続し直し | 連携の解除 | 状態 |
|---|---|---|---|---|---|---|---|
| Meta Muse | URL | 済 | 済 | 済 | 未 | 未 | 確認中（2026-11-09 に読み取り・下書きを確認。接続し直しと連携の解除が残る） |
| Claude Desktop | URL | 未 | 未 | 未 | 未 | 未 | 確認中 |
| Claude Code | URL | 済 | 済 | 済 | 済 | 済 | 確認済み（2026-11-15） |

Claude Code の確認（2026-11-15、運営者の Mac、Claude Code v2.1.195）: `claude mcp add --transport http <名前> <URL>` で追加し、`/mcp` の「Authenticate」で NexusInbox の許可の画面が開いて許可できた。受信箱の一覧と、新しいメッセージの本文を読めた。下書きはホームの「送信の確認」に出た。認証を消して許可し直すと再び読め、Web の「つながっている AI」から外すと読めなくなった。

確認で分かったこと:

- パソコンをつなぐ前に届いたメッセージは、パソコンの鍵に包まれていないため、URL 方式の AI では本文を読めない（一覧には出る）。AI は「このエージェントの今の鍵では開けません」と答える。初回のテストは、つないだ後の新しいメッセージ（自己宛の接続テスト）で行う。完了画面や AI 側の案内では、つなぐ前のメッセージは「受信したときの鍵があるブラウザや端末で確認してください」と伝える（別のブラウザでは Web でも読めないため、「Web で読めます」とは書かない）。
- `nexusinbox stop && nexusinbox start` を続けて実行すると、自動起動の登録の外しが終わる前に登録し直そうとして失敗し、止まったまま「Started」と表示されることがある（`scripts/run_noninteractive_stack.sh` の `start`）。パソコン側の不具合として直す。初回ガイドでは、`start` の表示ではなく、パソコンからの実際の接続（API に届いた最終接続）を確かめてから「接続しました」とする。起動処理の修正と実際の接続の確認を、段階 B の完了条件に含める。


### 5.3 接続手順

クラウド AI のコネクタ設定と、パソコンにプログラムを入れる手順は分ける。URL 方式の AI はパソコンの中継を通るため、AI を選ぶ前（選択肢）に「あなたのパソコンが通信を担当します。使っている間は起動しておく必要があります」と、必要な理由と続けて起動しておく条件を短く示し、③ の最初にパソコンをつなぐ手順を置く。

接続コードの期限、コピー、期限切れ時の再発行、再認証が必要な操作は既存部品を再利用する。秘密を含むコードを解析・計測基盤に送らない。名簿の署名・確認が完了するまで、単に資格情報が有効になったことを「安全に接続完了」と表示しない。

モバイルでパソコンが要る AI を選んだときは、エージェントを作る前に止め、「パソコンでこのページを開く」（URL のコピー）と「このスマホで Web だけ試す」を出す。進捗の引き継ぎは実装しないので「パソコンで続ける」とは書かない。パソコンでは同じ World ID でログインすること、招待から来た場合は宛先が URL に残ることを説明する。既存の同一人物向けブラウザ追加リンクと混同させない。

### 5.4 任せる範囲

初期値は自動対応なし。推奨を出す場合も、本人が対象と影響を確認して選ぶ。

| 選択 | 画面で必ず示す内容 |
|---|---|
| 自動対応しない | AI ツールの読み取り・下書き機能と、組み込みの自動返信は別である |
| 登録した相手に対応 | 対象となる相手、対応できる日程提案、タスク委任は確認が必要なこと |
| すべての相手に対応 | 未登録の相手も対象であること、対応できる依頼の種類と上限 |

任意のタスクを実行できるように見せない。Calendar が未接続なら空き時間を照会できるとは表示しない。Calendar を使わない日程返答の意味も設定時に説明する。

### 5.5 テストと完了表示

既存の自己宛テストを利用する。外部の相手には送らず、「接続テスト」と識別できるものにする。AI ツール側の読み取りはサーバで確かめる記録がないため、本人が「AI にテストメッセージが表示された／表示されなかった」を押し、「本人が確認」と表示する。接続の許可（OAuth の許可）は自動で確かめ、読み取りの確認とは別の行に出す。読み取りを確かめないまま後で続けることも認める。

| 検査 | 成功の根拠 | 失敗時の操作 |
|---|---|---|
| 受信 | テストメッセージが一覧に存在 | 再試行、後で続ける |
| Web で読む | この端末で復号できた | 鍵のある端末を案内 |
| AI で読む | テスト用ツール呼び出し成功、または本人の確認 | 接続先・権限・起動状況を確認 |
| 自動返答 | テストに紐づく送信成功を確認 | 設定・実行環境を確認 |

受信60秒、パソコンの返答180秒という既存の待機時間を初期値とする。時間切れは「失敗確定」とせず「まだ確認できません」。再試行で同じテストの重複送信を防ぐ。

完了画面の主要 CTA は「ホームへ」。未接続なら「Web で使い始められます。AI との接続はまだです」と表示する。紹介リンクの共有は補助操作にする。

進捗は再読み込み・ログイン後も再開できるようにする。再開時はサーバの設定と端末の鍵から再判定し、ローカルの完了フラグだけを信用しない。作成直後に離脱しても二重作成しない。

## 6. ホーム画面

### 6.1 配置

```text
ホーム                              [エージェントを選ぶ]

あなたの判断が必要  2件
  日程の候補が合いません             [候補を選ぶ]
  タスクを引き受けるか確認してください [内容を確認]

AI が対応したこと
  田中さんに日程候補を返信しました   10:24
  佐藤さんからの依頼を受け取りました 09:10
                                      [会話を見る]

自動対応の状態
  秘書: 最終確認 2分前                [設定] [自動返信を停止]
```

判断待ち0件は「今、あなたの操作が必要なものはありません」。取得失敗・読み込み中を0件表示に置き換えない。

エージェント選択は2つ以上あるときだけ表示する。1つの場合は名前だけを示し、0件なら初回ガイドへの操作を表示する。

判断待ちの件数には内訳を添える（例:「4件 — 送り主の確認 1・送信の確認 1・依頼への返答 1・受信の許可 1」）。件数だけで作業量を誤解させない。画面案は `docs/41_stage_a_home_mock.html`。

### 6.1.1 既存の知らせの統合先

| 現在の知らせ | ホームでの配置 | 会話画面の扱い |
|---|---|---|
| 「〇〇」にメッセージが届いていない（受け取る端末が未定） | 判断待ち。「端末を決める」への操作。本人が決めるまで相手からの送信が届かないため | 対象エージェントの会話一覧に短い理由と同じ操作 |
| まだメッセージがない（受信箱が空） | 初回体験・招待の補助案内。判断待ち件数に含めない | 空状態に短い説明とホームへのリンク |
| パソコンの接続を確認できない | 稼働状態。復旧操作が必要な場合だけ判断待ちにも同じ対象として参照 | 送信などの操作に影響するとき、その操作の近くに理由を表示 |
| 新しい端末・未承認の名簿 | 判断待ち。確認・承認への操作 | 対象会話に影響する場合だけ簡潔な警告 |
| 新しいバージョン | 更新の案内。稼働状態に併置 | 操作不能の原因でない限り常設しない |

#### 「あとで」

「あとで」を付けるのは、受け取る端末が未定のものと、パソコンが止まっているものの2種類だけとする。下書き・依頼・受信の許可・信頼の警告（送り主の確認不能、新しい端末）には付けない。

- あとでにしたものは判断待ちの件数から外すが、解消した扱いにはしない。判断待ちの一覧の最後に「あとでにしたもの N件」として常に残し、開けば元の操作ができる。
- パソコンの接続状況は、あとでにしても稼働状態に表示し続ける。
- 同じ問題（種類と対象IDが同じ）はポーリングで更新されても再表示しない。新しい端末や別の障害は新しい知らせとして判断待ちに出す。
- 記録は既存の「あとで」と同じくブラウザごとに保存し、サーバに送らない。端末未定はエージェント単位、パソコン停止は「その停止」単位（再び止まれば新しい知らせ）とし、既存の保存キーを引き継ぐ。

`NoticeCard`、`NewDeviceNotice`、`DeviceListNotice`、`StoppedComputerNotice` などの既存判定・操作を棚卸しして再利用する。知らせの種類と対象IDで同一性を管理し、ホームと会話の両方に同じ大きなカードを常設しない。ホームの状態と判断待ちに同じ問題を示す場合も件数は1件とする。スマホのスクロール修正を維持し、知らせが増えても本文や主要操作が押し出されて操作不能にならないことを確認する。

### 6.2 判断待ちの分類

| 種類 | 表示 | 主要操作 |
|---|---|---|
| 下書き承認 | 返信内容を確認してください | 下書きを確認 |
| 構造化依頼 | 日程候補／引き受けの判断 | 候補を選ぶ／内容を確認 |
| 送り主の確認不能 | 送り主を確かめられません | 理由を確認 |
| 新しい端末 | 新しい端末がつながりました | わたしがつないだ／心当たりがない場合は、端末を確認 |
| 受け取る端末が未定 | メッセージが届いていません | 端末を決める |
| 受信の許可（旧「確認が必要」） | 受信を許可するか確認してください | 決める（受け取る／捨てる／ブロック） |
| 実行環境の問題 | 自動対応を続けられません | 復旧方法を見る |

並び順は、信頼の警告（送り主の確認不能、新しい端末）→ 受け取る端末が未定 → 下書き承認・構造化依頼 → 受信の許可 → 実行環境の問題とする。受信の許可は「送信の確認」（下書き承認）と種類名で区別し、混同させない。

新しい端末に心当たりがない場合は、ホームに緊急停止を置かず、「心当たりがない場合は、端末を確認」で対象エージェントの端末画面へ移る。遷移先では該当端末を強調して最初に見える位置に出し、外す・緊急停止をそこで行えるようにする。

スパム承認待ち、AI 下書き、正規の依頼への判断待ちは種類を表示する。複数分類に該当する同じ対象を件数で重複計上しない。信頼警告がある場合は警告を先に解消し、ワンクリック承認で迂回しない。

一覧行は相手、依頼の要点、止まっている理由、主要操作1つで構成する。本文を復号できない端末では推測した要点を出さず、読める端末への案内を出す。

### 6.3 対応結果

受信・送信の事実と、仕事の結果を区別する。「返答を送りました」から「日程が確定しました」を推定しない。処理途中・失敗・送信結果不明を成功一覧に入れない。詳細から対応する会話と、適用した許可範囲を開けるようにする。

ホームには直近5件を出す。それより前の対応は、会話一覧を「AI の自動返信」で絞り込んだ状態で開く導線（「AI の対応をすべて見る」）から辿れるようにする。各行からは対応する会話を開ける。

最初は既存の監査イベントと構造化返信の事実を使う。本文を必要とする結果説明は端末で復号後に組み立てる。確かな事実を表せない場合は「自動返信を送信しました」に留める。

## 7. 会話詳細

### 7.1 状態と次の行動

会話上部に、現在の依頼の状態、最後に確認した出来事、次に動く主体を表示する。

| 状態 | 成立条件 | 表示例 |
|---|---|---|
| AI が対応中 | 実行開始を確認し、有効な処理中情報がある | 日程候補を確認しています |
| 相手の返事待ち | 有効な提案送信後、対応する返答が未到着 | 火曜14時を提案しました |
| あなたの判断待ち | 有効な承認・選択要求がある | 合う候補がありません |
| 完了 | その依頼の完了条件を満たすイベントを確認 | 選んだ候補への合意を確認しました |
| 停止・確認不能 | エラー、期限切れ、実行情報の鮮度切れ | 自動対応の状況を確認できません |

会話には複数依頼が存在し得る。状態は会話全体に単一の完了フラグを付けず、protocol ID と reply_to で関連付けた依頼単位に持つ。会話一覧では判断待ちを優先して要約し、他の進行中依頼の件数も示す。

### 7.2 状態判定規則

- 署名と文脈の検証に成功した構造化メッセージを根拠にする。
- 再送・重複受信を同一イベントとして扱う。矛盾する返答は自動で完了扱いにせず、履歴と確認案内を出す。
- accept は候補への合意であり、Calendar への登録完了を意味しない。
- task の accept は引き受けであり、complete とは別。LLM の本文だけから完了を認定しない。
- 期限切れでは操作時に再検査し、古いボタンから返答できないようにする。
- 旧形式や自由文の会話は「会話中」と表示し、状態を無理に推定しない。

送信者には「あなたが送信」「AI が自動返信」「AI が作成し、あなたが送信」を区別する。ただしサーバで根拠がない生成経路を推測してラベル付けしない。

### 7.3 段階 C で決めたこと（2026-11-15、画面案 `docs/41_stage_c_conversation_mock.html`）

- **依頼ごとの状態**: 会話の上に「この会話の依頼」を置き、依頼（最初の protocol ID と、それに reply_to でつながる返事）ごとに、状態・最後に確かめた出来事・次に動く主体を出す。あなたの番のときだけ操作を出す。
- **AI ツールにも同じ意味の状態**: ゲートウェイの `list_inbox`・`read_message` の結果に、Web と同じ意味の状態を付ける。取得した情報だけでは決められないときは「未確認」とし、1 通のメッセージから会話全体の状態を推測しない。状態と一緒に、根拠にしたメッセージ ID、確かめた時刻、履歴が足りないかどうかを返す。
- **会話一覧の札**: 判断待ちがある会話は「あなたの判断待ち」を先に出し、ほかに進行中があればその数も見えるようにする。送り主の確認失敗や履歴不足は「進行中」に混ぜず、別の札にする。完了・不成立は一覧に出さない。
- **終わった依頼**: 状態の欄で「終わった依頼 N 件」とたたむ。開いた中では「合意」「完了の連絡あり」「辞退」「期限切れ」を区別する。食い違いと履歴不足は未解決なので、たたまずに出す。
- **「AI が対応中」**: 対象の依頼のメッセージに、自動返信の処理を取った記録（`auto_reply_claimed_at`）があり、まだ返事を送っておらず（`auto_reply_sent_at` がない）、取った時刻から 3 分以内のときだけ。取り消された処理（記録が消える）は対応中ではない。時刻は記録された取得時刻で判定し、画面を読み直した時刻は使わない。3 分を過ぎたら「自動対応の状況を確認できません」とし、失敗や再送できるとは断定しない。

段階 C の実装（2026-11-15）:

- 判定は `packages/core/src/request-state.ts`（Web）と `services/agent-gateway/src/request_state.rs`（ゲートウェイ）の 2 つで、どちらも `tests/vectors/request_state.json` の 30 件を通す。通常の進行、重複受信、矛盾した返答、元の依頼がない、複数依頼と counter の関連付け、署名検証の失敗、履歴不足、期限切れ、処理開始から 3 分の境界、解除済み、送信結果不明を含む。
- Web: 会話の上に「この会話の依頼」（`RequestPanel`）。読めていない・送り主を確かめ中のメッセージがあれば「状態を確かめきれていません」と出す。会話一覧の札は会話のメッセージを読み終えてから出し、読めないものがあれば何も出さない（`lib/inbox/request-facts.ts`）。吹き出しには、自動返信の記録と下書き送信の記録（`agent_draft_sent`）があるものだけ「自動返信」「AI が作成し、あなたが送信」を付ける。
- 「AI が対応中」は「AI が対応を開始しました」と開始時刻を出し、続いているかどうかは分からないと書く。3 分を過ぎたら「その後の状況を確認できません」とし、送り直しを促さず、会話と送信済みのメッセージを確かめるよう案内する。
- ゲートウェイ: `read_message` は同じ相手とのメッセージ（スレッドがあればそのスレッド、なければ最新の受信・送信各 100 件のうち同じ相手のもの。最大 30 件）を読んで送り主を確かめ、そのメッセージの依頼の状態・説明・根拠のメッセージ ID・確かめた時刻・履歴不足の有無を `request_state` で返す。依頼の最初のメッセージ以降に読めないメッセージがあるとき（返事は必ず最初のメッセージより後なので、それより古い読めないメッセージは関係しない）、または元の依頼が読んだ範囲より古いかもしれないときは `unconfirmed`。Web から送る依頼にはスレッド ID が付かないため、相手ごとに集める（v0.9.0 の実機確認で、スレッドだけを見ると必ず `unconfirmed` になると分かった）。`list_inbox` は復号しないので、各メッセージの `request_state` は `unconfirmed`。

処理を取る記録の有効期間（2026-11-15 確認）: `auto_reply_claimed_at` には期限がない。処理を取ると `NOW()` が入り、返事を送ると `auto_reply_sent_at` が入る。送れなかった実行は記録を返して空に戻す（`DELETE /messages/{id}/auto-reply-claim`）。記録が残ったまま送られていない行は「試みたが確かめられなかった」として自動返信の対象から外れ、本人に残る（docs/29 §2.5、migration 0019）。期限がないので、3 分の判定は記録された取得時刻だけから行い、ほかの期限とずれることはない。パソコンの実行は 30 秒ごとで、取ってから送るまでは通常数秒のため、3 分は余裕のある初期値になる。

## 8. 稼働状態と一時停止

設定と実行を別々に表示する。自動対応 ON は、プログラムが動いている証拠ではない。

| 状態 | 根拠 | 文言 |
|---|---|---|
| 無効 | サーバの設定 OFF | 自動対応はオフです |
| このブラウザで実行可能 | 必要な鍵・設定・実行画面が揃う | この画面を開いている間、自動対応できます |
| 最近の接続を確認 | パソコンの既存の最終接続情報が新しい | 接続を2分前に確認しました |
| 接続が古い | 既存の接続判定しきい値を超過 | 接続をしばらく確認できていません |
| 状況不明 | 状態 API の取得失敗 | 状態を取得できません。再確認してください |
| 実行中 | 対象依頼の処理中情報が新しい | この依頼に対応中です |

`agent-status.ts` の現行の判定を初期実装で共有し、画面ごとにしきい値を重複定義しない。追加の heartbeat は必要性を測定してから導入する。最近の接続だけで「すべて正常」と断定しない。

停止操作は次の3つを区別し、単独の「一時停止」という曖昧なラベルは使わない。

| 操作 | 止まるもの | 続くもの・注意 |
|---|---|---|
| 自動返信を停止 | 対象エージェントの組み込み自動返信 | AI の読み取り・下書き作成・本人が許可する送信は別。連携解除ではない |
| クラウド AI との連携を終了 | 既存の「使うのをやめる」で対象となるクラウド接続 | 自動返信設定やローカル連携まで止まるとは表示しない。実際の失効対象と反映待ち時間を説明 |
| 緊急停止 | 既存の緊急停止が失効させる資格情報・トークン・AI 接続 | 詳細設定の強い操作として残す。再開には再接続などが必要 |

ホームで提供するのは「自動返信を停止」。対象エージェントを明示し、保存中は二重操作を防ぎ、成功後だけ停止を表示する。「これからの自動返信を停止しました。送信済みの内容は取り消せません」と伝える。再開も同じ場所から可能にする。停止が実行中の処理に反映される時点は既存 executor の仕様に合わせ、即時に全処理を中断したとは表示しない。連携終了・緊急停止の具体的な失効範囲は実装時に既存 API と照合する。

## 9. ブロックと通報

| 操作 | 範囲 | UI の扱い |
|---|---|---|
| L1「この相手だけ」 | 自分宛の該当送信元 | 既存機能を維持 |
| L2「この人のすべてのエージェント」 | 同じ人の全エージェントから自分への連絡 | 推奨する説明。新規エージェントにも効く旨を示す |
| L3「完全に非表示」 | 現行 L3 の相手からの可視性制限 | 影響を確認して実行 |
| 通報 | 運営への調査依頼 | 将来追加。未実装の間は操作を出さない |
| 利用停止 | 運営がサービスの利用を制限 | 個人のブロックと別の運用設計が必要 |

確認文例:「この人が持つすべてのエージェントから、あなたへの連絡を止めます。新しいエージェントを作り直しても届きません。」

解除場所を完了時に表示する。利用者がブロックしただけで「この人は誰にも送れません」「サービスから BAN しました」と表示しない。

既存メニューと一覧との対応は L1「この相手だけ」、L2「この人のすべてのエージェント」、L3「完全に非表示」を維持する。本書の「この人からの連絡を止める」は L2 の説明であり、別の第4段階を作らない。会話のブロックメニュー、確認ダイアログ、完了通知、コンタクトの「ブロック中」で同じ段階名を使う。「この人」は World ID の証明に紐づく同一の送信主体を意味し、実名の特定や善意の認定を意味しない。

## 12. 計測と利用者テスト

### 12.1 データを増やさない評価方針

利用者ごとの行動計測は導入しない。アナリティクス目的の Cookie、端末ID、行動イベント保存、セッションリプレイを追加しない。現在のプライバシーポリシーと、運営がデータを極力持たない方針を維持する。

主な評価は §12.2 の参加者の同意を得た観察テストで行う。テスト中に、接続までの時間、判断までの操作、復旧できたかを記録して改善に使う。本番利用者の行動ログとして常時収集しない。

必要に応じ、業務上すでに保持する表からエージェント数・有効な接続数などの全体件数だけを集計する。個人・端末を追跡せず、新しい識別子や表を作らない。少人数を特定できる細分化や公開は行わない。これらの数をオンボーディング到達率の代わりとはしない。

### 12.2 利用者テスト

AI ツール利用者と Web から試す利用者を含め、まず5人程度で観察する。これは統計的な品質保証ではなく、つまずきの発見に使う。

1. 説明を見たあと、自分の言葉でサービスの役割を説明できるか。
2. 接続後、何が動き、どの条件で止まるか説明できるか。
3. ログを全件読まず、AI が何をし、自分が何をすべきか答えられるか。
4. 自動対応の範囲を確認して変更・停止できるか。
5. ブロックの効果が自分宛なのかサービス全体なのか区別できるか。

数値目標は初回観察の基準値を得てから設定する。説明できない箇所は、機能追加より先にラベルと順序を見直す。

## 13. 実装順と受け入れ条件

### 段階 A: ホームの優先順位

実装前に、デスクトップとスマホの画面案を作成してレビューする。0件、判断待ちあり、取得失敗、接続不明、新しい端末、複数エージェントを含め、`/pending` の統合と知らせの配置を確認してから実装する。

既存データで判断待ち、対応結果、状態要約を実装し、会話一覧への導線と既存 URL 互換を整える。

実装済み（2026-11-15）:

- `/` がホーム、会話一覧は `/conversations`。`/` に `with`・`as`・`agent`・`view` が付いた入口と `/agent/:did` は `/conversations` へ、`/pending` は `/#attention` へ転送する（`next.config.ts`）。
- 判断待ちは `lib/home/`（`attention.ts` で並び順・重複・内訳、`put-off.ts` で「あとで」、`device-attention.ts` で端末の確認）。入るのは、端末の一覧の不一致・接続コードの不一致・新しい端末・受け取る端末が未定・AI の下書き・受信の許可・止まったパソコン。
- 会話一覧の上の端末の知らせ（3 枚）はやめ、自動で行っていた処理（接続コードの確定、ひとつだけのブラウザの承認、初めて見た端末の記録）は `DeviceUpkeep` としてホームと会話で動かす。ブラウザの自動返信もホームで動く。
- 対応結果は `auto_reply_sent` の直近 5 件。「AI の対応をすべて見る」は `/conversations?filter=auto`（「AI の自動返信」の札）。会話一覧は 1 ページ分（100 件）から絞り込む。
- 端末の画面は `?device=<DID>` のとき、その端末を先頭に出して印を付け、見える位置に動かす。
- 判断待ちにまだ入れていないもの: 送り主の確認不能と構造化依頼（本文の復号が要るため段階 C で扱う）、実行環境の問題（判定元がないため、稼働状態では「状態不明」として扱う）。そのため 0 件のときは「ホームで確認できる判断待ちはありません」とし、「日程などの依頼は「会話」で確認できます」から会話一覧へ案内する。確認済みに読める「操作が必要なものはありません」は使わない。
- 受信の許可は 100 件ずつ読み込む。件数と内訳はサーバの総数で数え、読み込んでいない分は「ほかに N 件あります」と「続きを読み込む」で示す。エージェントで絞ったときは、未読み込みの分は宛先が分からないため件数に含めず、別に表示する。
- クラウドの AI への案内文（ゲートウェイの `create_draft`）は「確認が必要」から「ホーム」に変えた。コンピュータ側の次のリリースで反映される。

- 未読と判断待ちが独立している。
- 読み込み中、0件、取得失敗が区別される。
- 同じ対象を件数で重複計上しない。
- データの取得範囲を超えた「すべて完了」を表示しない。
- デスクトップと幅320 CSS pxで主要操作に到達できる。
- URL 棚卸しで列挙した既存の入口が、移行後もすべて元の目的の画面・対象に到達する。`/pending`、通知、`/?with=…`、ログイン後の戻り先を E2E で確認する。
- デスクトップとスマホのナビが一致し、旧「確認が必要」の操作をホームから行える。
- 既存の知らせの重複がなく、スマホで知らせが増えてもスクロールと会話操作が維持される。

### 段階 B: 初回成功体験

実装前に、ログイン前から初回完了までの画面案を作りレビューする。Web 試用と確認済み AI ツール別の経路、未接続、再開、期限切れ、再認証、モバイルで別端末が必要な場合を含める。

AI 選択、共通の作成・接続手順、権限の説明、能力別テストと再開を実装する。

実装済み（2026-11-15）:

- ログイン前（`/login`）は見た目を変えず、§4.1 の文言、「体験例」の札、World ID を使う理由（ボタンの前）、「使い方を見る」にした。
- `/onboarding` は「AI を選ぶ → 連絡先を作る → AI とつなぐ → 任せる範囲 → 試す → 準備状況」。選べる AI は確認済みの Claude Code と「まず Web で試す」だけで、Muse と Claude Desktop は「確認中」で選べない。エージェントのない人がホームを開くと初回ガイドへ移る。
- AI とつなぐ: パソコンの接続は API に届いた最終接続で判断し、クラウドの AI を使えるようにして URL と `claude mcp add` のコマンドを出し、許可（OAuth の grant）が届くまで待つ。許可がなければ「あとでつなぐ」だけを出す。
- スマホでパソコンが要る AI を選ぶと、作る前に「パソコンでこのページを開いてください」（URL のコピー）と「このスマホで Web だけ試す」を出す。
- 試す: 受信・Web で読む・AI の許可（自動）・AI で読む（本人が確認、あとでも可）・自動返答を別々の行にする。待ち時間を過ぎたら「まだ確認できません」と「もう一度確かめる」（送り直さない）。
- 続きから: URL の `agent` と `ai`、サーバの許可、この端末の鍵から判定する（`lib/onboarding/flow.ts`）。鍵がない端末では作り直させず、作ったブラウザへ案内する。

- 新規利用者が既存の手動手順を探さず、試用または接続へ進める。
- 未接続、一部成功、タイムアウト、再認証、鍵確認不一致を区別する。
- 再読み込み・期限切れ・戻る操作で二重作成やテスト多重送信が起きない。
- クラウド AI の下書き専用経路を自律送信成功として表示しない。

### 段階 C: 会話の状態

日程調整とタスク委任から依頼単位の状態を表示する。

- 送信成功を仕事の完了と表示しない。
- 署名不正、返答の矛盾、期限切れ、古い履歴の欠落を安全に扱う。
- 複数依頼、counter、相手待ち、担当者判断を説明できる。
- Web と AI ツール向けの状態説明で意味が一致する。

### 段階 D: 改善の評価

観察テストと、必要なら既存データの全体集計で、どの手順が理解や接続を妨げるかを確認する。必要に応じて復旧手順と導入順を改善する。各段階の画面変更は画面案のレビューを経て実装する。

### 検証方法

状態導出には意味のある入出力テストを追加する。E2E は「初回試用」「AI 接続と確認」「判断待ちから対応」「異常から復旧」「既存会話 URL」の代表フローを対象とする。モックで到達する確認と、実際の AI ツール・パソコン・スマホを使った確認を記録上区別する。

セキュリティ上の名簿・署名・承認・再認証の制約は既存設計を維持する。導入を短くするために検証を省略しない。段階ごとの PR ではこの設計と実装済み箇所を更新する。
