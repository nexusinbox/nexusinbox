決めたいこと（考え方）

  • 状態は会話全体ではなく依頼ごと（最初の依頼の protocol ID と、それに reply_to でつながる返事）に持つ。1 つの会話に依頼が複数あれば、判断待ちを先頭に並べる。
  • 根拠にするのは、送り主を確かめられた（署名 v2・端末名簿）構造化メッセージだけ。確かめられないものは状態に含めず、その旨を出す。自由文だけの会話には状態を付けない（「会話中」とも出さない）。
  • 「送れた」ことと「仕事が終わった」ことを分ける。日程の承諾は「候補に合意」で、予定表への登録とは書かない。タスクの引き受けは「引き受けた」で、完了は相手からの完了の連絡（complete）が来たときだけ。
  • 次に動くのはだれかを 1 行で書く（あなた／相手／AI）。あなたの番のときだけ、操作ボタンを状態の欄に出す。
  • 期限を過ぎた依頼は、古いボタンから返事できないようにする（押す時にも期限を確かめ直す）。
  • 吹き出しの上に「あなたが送信」「AI が自動返信」「AI が作成し、あなたが送信」を出す。根拠はサーバの記録（自動返信の記録、下書きの送信記録）だけで、推測はしない。

状態の決め方

依頼最後の確かな出来事状態次に動く
日程調整こちらが提案（propose）／別の候補（counter）を送った相手の返事待ち相手

どちらかが辞退（decline）不成立—
返事の期限を過ぎた期限切れ—
承諾と辞退が両方ある、違う候補に承諾、など返事が食い違っているあなた（履歴を確かめる）
タスク依頼（delegate）を送った／届いた相手の返事待ち／あなたの判断待ち相手／あなた

辞退（decline）不成立—

決まったこと（2026-11-15）

  • AI ツール（list_inbox・read_message）にも同じ意味の状態を付ける。取得した情報だけで決められなければ「未確認」。1 通から会話全体を推測しない。根拠のメッセージ ID・確かめた時刻・履歴不足の有無も返す。
  • 会話一覧は判断待ちを先にし、ほかの進行中の数も見えるようにする。送り主の確認失敗と履歴不足は「進行中」に混ぜない。
  • 終わった依頼はたたみ、開いた中で「合意」「完了の連絡あり」「辞退」「期限切れ」を分ける。食い違い・履歴不足はたたまない。
  • 「AI が対応中」は、その依頼のメッセージに処理を取った記録があり、未送信で、取った時刻から 3 分以内のときだけ。取り消された処理は対象外。3 分を過ぎたら「確認できません」（失敗とは言わない）。処理を取る記録には期限がないので、時刻は記録された取得時刻だけで判定する。
