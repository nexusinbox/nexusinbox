# 42. 段階 D: 問い合わせと評価から直す

ステータス: Accepted（2026-11-16）

docs/41 §12・§13 段階 D の具体化。テスターを集めた観察テストは行わない（2026-11-16 決定）。実際に使い始めた人からの問い合わせ・感想・不具合の報告をもとに、使い勝手を少しずつ直す。無償のサービスなので、いまは「安全に、安心して使えること」を最優先にし、使い勝手は磨き込みながら進める。

## 1. 守ること

- **データを増やさない**（docs/41 §12.1）。利用者ごとの行動計測、Cookie や端末 ID による追跡、セッションの録画は入れない。改善の材料は、利用者が自分から送ってくれたものだけにする。
- **受け取った内容を広げない**。問い合わせに書かれたアドレス・メッセージの内容・連絡先は、対応に使う範囲だけで扱い、公開の場（issue など）に写さない。公開する場合は、本人が分からない形に書き直す。
- **セキュリティを先に**。脆弱性の報告は使い勝手の話より先に扱い、直すまで内容を公開しない（`SECURITY.md`）。公開のコミットメッセージに、直していない脆弱性を書かない。

## 2. 受け取る窓口

| 窓口 | 受け取るもの | 置き場所 |
|---|---|---|
| 問い合わせフォーム（Google フォーム） | 感想、使いにくい点、困りごと、データの開示・削除の依頼 | メニューの「お問い合わせ」、ヘルプのいちばん下の「ご意見・お問い合わせ」、プライバシーポリシー・利用規約の末尾 |
| 公開リポジトリの issue | 不具合、機能の要望（公開されてよいもの） | `nexusinbox/nexusinbox` |
| 脆弱性の報告 | セキュリティの問題 | `SECURITY.md` の手順（公開の issue にしない） |

## 3. 受け取ったあとの扱い

1. **振り分け**: セキュリティ（安全・秘密・なりすまし）／壊れている（使えない、データが見えない）／使い勝手（分かりにくい、迷う）／要望 の 4 つに分ける。
2. **順番**: セキュリティ → 壊れている → 使い勝手 → 要望。
3. **使い勝手の直し方**: 機能を足す前に、ラベルと順序を見直す（docs/41 §12.2）。同じ箇所に 2 件以上の声が集まったものから直す。画面の変更は、これまでどおり画面案を見てから実装する。
4. **記録**: 直したものと理由を docs/41（または該当する設計書）に残す。個人を特定できる内容は書かない。

## 4. 全体の件数（任意）

規模を見るときだけ、すでにある表から**件数だけ**を運営者が手で数える（エージェントの数、有効なパソコンの接続の数、クラウドの AI の許可の数）。個人や端末をたどれる切り方はせず、新しい表や識別子を作らず、公開しない。これらの数を初回ガイドの到達率の代わりにはしない（docs/41 §12.1）。

## 5. 当面の重点

- **安全**: コード全体のセキュリティ監査を行い、見つかったものを直す（2026-11-16 開始）。
- **使い勝手**: 問い合わせと感想を待ちながら、明らかな崩れや食い違い（画面と説明の不一致など）を見つけしだい直す。
- Muse・Claude Desktop の確認（docs/41 §5.2.1）は、実機で 5 項目が済んだときに選択肢へ加える。
